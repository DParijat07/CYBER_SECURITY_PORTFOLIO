# Web Monitoring

## 1. Introduction

Web monitoring is the process of collecting, analyzing, and correlating security telemetry generated by web applications, web servers, reverse proxies, Web Application Firewalls (WAFs), and related infrastructure.

Web monitoring helps SOC analysts detect:

* Web application attacks
* Unauthorized access
* Web scanning
* SQL injection
* Cross-Site Scripting (XSS)
* Path traversal
* Command injection
* Authentication attacks
* Exploitation attempts
* Suspicious web requests
* Web shells
* Data exfiltration

A SOC analyst should monitor both **the request** and **what happened after the request**.

```text id="qz7z2f"
Internet
   ↓
Web Application / Web Server
   ↓
WAF / Reverse Proxy
   ↓
Application Logs
   ↓
SIEM
   ↓
SOC Analyst
```

---

## 2. Why Web Monitoring Is Important

Web applications are exposed to potentially untrusted users and Internet traffic.

Attackers may attempt to:

* Discover hidden endpoints
* Identify application technologies
* Exploit vulnerabilities
* Steal credentials
* Access unauthorized resources
* Execute commands
* Upload malicious files
* Establish persistence
* Extract sensitive information

Web monitoring provides visibility into these activities.

---

## 3. Objectives of Web Monitoring

The primary objectives are:

1. Detect malicious web requests
2. Identify reconnaissance and scanning
3. Detect authentication attacks
4. Identify application-layer exploitation
5. Monitor abnormal HTTP/HTTPS behavior
6. Detect suspicious file uploads
7. Identify web shells
8. Detect unauthorized access
9. Correlate web activity with endpoint telemetry
10. Support incident investigation

---

## 7. HTTP Status Codes

Important status codes include:

| Code    | Meaning               | Security Relevance                               |
| ------- | --------------------- | ------------------------------------------------ |
| 200     | OK                    | Successful request                               |
| 201     | Created               | Resource created                                 |
| 301/302 | Redirect              | May be normal or suspicious                      |
| 400     | Bad Request           | Possible malformed request                       |
| 401     | Unauthorized          | Authentication failure                           |
| 403     | Forbidden             | Access-control violation                         |
| 404     | Not Found             | Possible scanning                                |
| 405     | Method Not Allowed    | Possible enumeration                             |
| 429     | Too Many Requests     | Possible abuse/rate limiting                     |
| 500     | Internal Server Error | May indicate exploitation or application failure |
| 502     | Bad Gateway           | Infrastructure/application issue                 |
| 503     | Service Unavailable   | Service disruption                               |

A single status code is rarely sufficient to identify an attack.

## 8. Web Reconnaissance Monitoring

Attackers frequently perform reconnaissance before exploitation.

Indicators include:

```text id="v7p0r4"
Large number of 404 responses
Repeated requests to unusual paths
Requests for backup files
Requests for configuration files
Requests for administrative endpoints
Requests for known vulnerable paths
Automated User-Agent strings
High request frequency
```

Example:

```text id="6i8xzx"
GET /admin
GET /backup
GET /.env
GET /config.php
GET /wp-admin
GET /phpinfo.php
```

A sequence of these requests may indicate automated reconnaissance.

---

## 9. SQL Injection Monitoring

SQL injection attempts may appear in HTTP requests.

Common indicators include suspicious SQL syntax such as:

```text id="1o8lcz"
'
"
OR 1=1
UNION SELECT
SELECT
SLEEP(
WAITFOR DELAY
```

Example:

```text id="j6z0jy"
GET /user?id=1' OR '1'='1
```

Another example:

```text id="7g4w9s"
GET /product?id=1 UNION SELECT username,password FROM users
```

SOC analysts should correlate suspicious requests with:

* Application errors
* Database logs
* WAF alerts
* Response codes
* Endpoint activity

---

## 10. Cross-Site Scripting Monitoring

XSS attempts may contain suspicious script-related input.

Example:

```text id="v0txc3"
<script>alert(1)</script>
```

Potential indicators:

* Script tags in parameters
* JavaScript payloads
* Encoded script content
* Suspicious HTML input
* Repeated requests containing similar payloads

WAF alerts and application logs can help identify these attempts.

---

## 11. Path Traversal Monitoring

Path traversal attempts try to access files outside the intended application directory.

Example:

```text id="v8u2u7"
GET /download?file=../../../../etc/passwd
```

Common indicators include:

```text id="9d4x7n"
../
..\
%2e%2e%2f
%2e%2e%5c
```

A successful path traversal attempt should be correlated with endpoint and file-access telemetry.

---

## 12. Command Injection Monitoring

Command injection occurs when an attacker attempts to execute operating-system commands through a vulnerable application.

Potential indicators include:

```text id="k8fj9c"
;
&&
||
|
$(...)
`...`
```

Example:

```text id="9o8j3m"
GET /ping?host=8.8.8.8;whoami
```

If the request is followed by a process such as:

```text id="h6z0yb"
www-data
   ↓
/bin/sh
   ↓
whoami
```

the event becomes significantly more suspicious.

---

## 13. Authentication Monitoring

Web applications should be monitored for:

* Repeated failed logins
* Successful login after failures
* Login from unusual IPs
* Login from unusual countries
* Account enumeration
* Password-reset abuse
* MFA failures
* Session anomalies

Example:

```text id="9x5x4v"
50 failed logins
       ↓
Successful login
       ↓
New source IP
       ↓
Sensitive account activity
```

This may indicate credential compromise.

---

## 14. File Upload Monitoring

File upload functionality can be abused to deliver malicious files.

Monitor:

* File names
* File extensions
* MIME types
* File hashes
* Upload source
* Upload destination
* User identity
* Subsequent execution

Example suspicious sequence:

```text id="j3a0z1"
POST /upload
      ↓
shell.php
      ↓
Upload successful
      ↓
GET /uploads/shell.php
      ↓
Server-side execution
```

This may indicate a web-shell attack.

---

## 15. Web Shell Detection

A web shell is malicious code placed on a web server to allow unauthorized remote interaction.

Potential indicators include:

* New executable scripts in web directories
* Unexpected file creation
* Requests to unusual script files
* POST requests to suspicious endpoints
* Web server process spawning command shells
* Outbound connections from the web server

Example:

```text id="k5j7hm"
Internet
   ↓
Web Server
   ↓
Malicious PHP File
   ↓
Command Execution
   ↓
Outbound Connection
```

Endpoint telemetry is extremely valuable for confirming web-shell activity.

## 17. Web Scanning Detection

Automated scanners often generate recognizable request patterns.

Indicators include:

```text id="s6k2jv"

Many 404 responses
Many different endpoints
Repeated requests with identical User-Agent
Requests for known vulnerable files
Requests for administrative interfaces
```

Example:

```text id="x6q0c5"

800 × HTTP 404
120 × HTTP 403
50 × HTTP 200
30 × HTTP 500
```

The sequence may represent automated reconnaissance.

Web attacks should be correlated across multiple telemetry sources.

Example:

```text id="3h9g5m"

    ↓
```

## 21. Example Detection Rules

### Rule 1 — Web Scanning

```text id="f7r0cr"
IF
source IP generates
more than 100 HTTP 404 responses
within 5 minutes

THEN
generate reconnaissance alert
```

```text id="q5w3a8"

```


## 23. SOC Triage Process

### Step 1 — Identify the Request

Determine:

```text id="8x0n5d"
Source IP
Destination
URI
HTTP method
Timestamp
User-Agent
```

### Step 2 — Identify the Attack Pattern

Look for:

```text id="9m4k8s"
SQL injection
XSS
Path traversal
Command injection
Scanning
Authentication abuse
File upload
```

### Step 3 — Check WAF

Determine:

```text id="x5q8t1"
Was the request blocked?
Was it allowed?
Which rule triggered?
```

### Step 4 — Check Application Logs

Look for:

```text id="b7y3w0"
Errors
Exceptions
Authentication events
Unexpected application behavior
```

### Step 5 — Check Database Logs

Determine whether suspicious queries reached the database.

### Step 6 — Check Endpoint Telemetry

Look for:

```text id="m9v6s2"
New processes
New files
Web-shell activity
Command execution
Network connections
```

### Step 7 — Determine Impact

Ask:

```text id="v3x8q0"
Was exploitation successful?
Was data accessed?
Was persistence established?
Was the server compromised?
```

### Step 8 — Classify and Escalate

Classify the alert and escalate confirmed incidents according to the organization's incident-response procedure.

## 24. Web Monitoring Best Practices

Organizations should:

* Centralize web logs
* Monitor WAF alerts
* Monitor authentication activity
* Protect administrative endpoints
* Monitor file uploads
* Monitor web directories
* Establish normal traffic baselines
* Detect abnormal request rates
* Integrate web logs with SIEM
* Correlate application and database telemetry
* Monitor server processes
* Protect and retain logs
* Regularly review detection rules
* Use secure application-development practices

## 26. Key Takeaways

Web monitoring provides the SOC with visibility into attacks targeting Internet-facing applications and web infrastructure.

A SOC analyst should understand:

* HTTP/HTTPS traffic
* Web server logs
* WAF alerts
* Authentication events
* Web reconnaissance
* SQL injection
* XSS
* Path traversal
* Command injection
* Malicious file uploads
* Web shells
* API abuse
* Application and database correlation

The key investigation model is:

```text id="9u3v1e"
Request
  ↓
Detection
  ↓
Application Response
  ↓
WAF / Application Logs
  ↓
Database Activity
  ↓
Endpoint Activity
  ↓
Network Activity
  ↓
Impact Assessment
  ↓
Incident Response
```

**Web monitoring is most effective when the SOC does not treat HTTP requests as isolated events. The analyst should correlate web activity with WAF, application, database, endpoint, identity, and network telemetry to determine whether an attack was merely attempted or actually succeeded.**

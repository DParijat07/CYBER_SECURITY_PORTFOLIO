# Security Monitoring Configuration

## 1. Purpose

This document explains how the Ubuntu 22.04 LTS endpoint is prepared for security monitoring in the Linux Security Monitoring Lab.

The objective is to configure the Linux endpoint so that important security-related activities can be observed and later collected by the Wazuh Agent.

This stage focuses on:

* Understanding the monitoring scope
* Identifying the Linux telemetry sources to monitor
* Confirming that required services are available
* Preparing authentication monitoring
* Preparing system and service monitoring
* Preparing process and shell activity monitoring
* Configuring the Wazuh Agent for basic Linux log monitoring
* Validating that the monitoring configuration is working

The lab uses the following primary monitoring architecture:

```text
Ubuntu 22.04 LTS
       ↓
Linux Events
       ↓
Local Logs / Security Telemetry
       ↓
Wazuh Agent
       ↓
Wazuh Server
       ↓
Detection
       ↓
Alert Analysis
```

---

# 2. Monitoring Scope

The Linux Security Monitoring Lab monitors the following activity categories.

| Monitoring Area    | Examples                           |
| ------------------ | ---------------------------------- |
| Authentication     | Failed login, successful login     |
| Privilege Activity | `sudo` usage                       |
| User Activity      | Account-related activity           |
| Process Activity   | Process execution                  |
| Shell Activity     | Command execution                  |
| Service Activity   | Service start/stop                 |
| System Activity    | System events and errors           |
| File Activity      | Selected security-relevant changes |

The purpose is not to monitor every possible Linux event.

The goal is to collect enough useful security telemetry to support beginner-level SOC investigation.

The configuration in this lab is based on the following components.

## 5.1 Ubuntu 22.04 LTS

The Ubuntu VM is the endpoint being monitored.

It generates events from:

* Users
* Authentication services
* System services
* Applications
* Processes
* The operating system

## 5.2 systemd-journald

`systemd-journald` records events generated by the operating system and services.

It can be inspected using:

```bash
sudo journalctl
```

---

## 5.3 Authentication Logs

Ubuntu commonly provides authentication-related information through:

```text
/var/log/auth.log
```

This is important for monitoring:

* SSH authentication
* Failed login attempts
* Successful login attempts
* `sudo` activity

---

## 5.4 System Logs

General system messages can commonly be found in:

```text
/var/log/syslog
```

These logs can help with:

* Service monitoring
* System troubleshooting
* System activity analysis
* Security investigations

---

## 5.5 Wazuh Agent

The Wazuh Agent runs on the Ubuntu endpoint.

Its role in this lab is:

```text
Collect Endpoint Security Telemetry
                ↓
       Send to Wazuh Server
                ↓
      Centralized Monitoring
```

The agent configuration file is:

```text
/var/ossec/etc/ossec.conf
```

# 6. Pre-Configuration Checks

Before configuring monitoring, verify that the Ubuntu endpoint is working correctly.

## 6.1 Check Operating System

Run:

```bash
lsb_release -a
```

Expected result should identify Ubuntu 22.04 LTS.

You can also run:

```bash
cat /etc/os-release
```

---

## 6.2 Check Systemd

Run:

```bash
systemctl --version
```

This confirms that the system is using `systemd`.

---

## 6.3 Check Journal Service

Run:

```bash
systemctl status systemd-journald
```

The service should normally show as active.

---

## 6.4 Check Authentication Log

Run:

```bash
sudo ls -l /var/log/auth.log
```

If the file exists, inspect it with:

```bash
sudo tail -n 10 /var/log/auth.log
```

---

## 6.5 Check System Log

Run:

```bash
sudo ls -l /var/log/syslog
```

Then:

```bash
sudo tail -n 10 /var/log/syslog
```

# 7. SSH Monitoring Preparation

SSH is an important source of authentication events in a Linux SOC lab.

Check whether SSH is installed and running:

```bash
systemctl status ssh
```

If SSH is installed and active, it can generate events such as:

```text
Failed authentication
Successful authentication
Connection attempt
Session activity
```

These events can later be used for detection and investigation exercises.

Do not change SSH security settings unnecessarily at this stage.

---

# 8. Sudo Monitoring Preparation

`sudo` provides a controlled way to generate privilege-related activity.

Check whether the current user can use sudo:

```bash
sudo -l
```

Then perform a harmless test:

```bash
sudo whoami
```

Expected output:

```text
root
```

Afterward, inspect the authentication log:

```bash
sudo grep "sudo:" /var/log/auth.log
```

The exact log format can vary between systems.

---

# 9. Process Monitoring Preparation

Linux process activity is an important part of endpoint security monitoring.

Basic process information can be viewed using:

```bash
ps aux
```

A simpler view is:

```bash
ps
```

You can also use:

```bash
top
```

to observe running processes.

The objective at this stage is to understand the endpoint's process activity.

Detailed process monitoring and investigation will be covered in later documentation.

---

# 10. Shell Activity Preparation

The Linux shell is an important source of user activity.

For the current shell, identify the shell:

```bash
echo $SHELL
```

Identify the current user:

```bash
whoami
```

Display the current command history:

```bash
history
```

Shell history should not be treated as a complete security log.

It can be useful as supporting information, but centralized security monitoring requires appropriate telemetry from the endpoint.

# 12. Wazuh Agent Configuration File

The primary Wazuh Agent configuration file is:

```text

```

Before making changes, create a backup:

```bash
sudo cp /var/ossec/etc/ossec.conf /var/ossec/etc/ossec.conf.backup
```

This provides a simple recovery point if a configuration mistake is made.

---

# 13. Configure Linux Log Monitoring

Wazuh can monitor Linux log files through the `localfile` configuration.

The configuration follows this general structure:

```xml
<localfile>
  <location>/var/log/auth.log</location>
  <log_format>syslog</log_format>
</localfile>
```

For the system log:

```xml
<localfile>
  <location>/var/log/syslog</location>
  <log_format>syslog</log_format>
</localfile>
```

These entries tell the Wazuh Agent which local log files should be monitored.

The exact configuration must be placed inside the appropriate `<ossec_config>` section of:

```text
/var/ossec/etc/ossec.conf
```

Do not create duplicate entries if the same log source is already configured.

# 18. Configuration Validation

Configuration validation must be performed separately from the setup process.

The objective is to confirm that:

1. Ubuntu is generating logs.
2. The Wazuh Agent is running.
3. The configured log sources exist.
4. The Wazuh Agent can read the required logs.
5. New events can be generated.
6. The events can reach the Wazuh Server.

---

# 19. Validation Step 1 — Verify Linux Logs

Run:

```bash
sudo tail -n 10 /var/log/auth.log
```

Then:

```bash
sudo tail -n 10 /var/log/syslog
```

Confirm that log entries are being generated.

Record the observation in the Evidence directory.

---

# 20. Validation Step 2 — Verify Wazuh Agent

Run:

```bash
sudo systemctl status wazuh-agent
```

Confirm that the service is active.

Also check:

```bash
sudo tail -n 30 /var/ossec/logs/ossec.log
```

Look for obvious errors.

---

# 21. Validation Step 3 — Generate a Controlled Event

Perform a harmless sudo command:

```bash
sudo whoami
```

Then inspect:

```bash
sudo grep "sudo:" /var/log/auth.log
```

Confirm that the activity generated a log entry.

---

# 22. Validation Step 4 — Generate a Controlled Authentication Event

From an authorized lab machine, perform a controlled SSH authentication attempt against the Ubuntu VM.

For example, use an intentionally incorrect password once.

Then inspect:

```bash
sudo grep "Failed password" /var/log/auth.log
```

The objective is to verify that the endpoint records the event.

Do not perform repeated password guessing.

---

# 23. Validation Step 5 — Verify Successful Authentication

Perform a normal authorized SSH login.

Then run:

```bash
sudo grep "Accepted" /var/log/auth.log
```

Confirm that the successful authentication event is visible.

---

# 24. Validation Step 6 — Verify Centralized Collection

Open the Wazuh Dashboard on the Wazuh Server.

Locate the Ubuntu endpoint and verify that it is connected.

Then look for newly generated Linux events.

The expected path is:

```text
Controlled Activity
        ↓
Ubuntu Event
        ↓
Local Log
        ↓
Wazuh Agent
        ↓
Wazuh Server
        ↓
Wazuh Dashboard
```

The exact dashboard view may vary depending on the Wazuh version and configuration.

---

# 25. Validation Step 7 — Compare Local and Central Events

For at least one test event, compare:

```text
Local Ubuntu Log
        ↕
Wazuh Event
```

Record:

* Approximate timestamp
* Event type
* Username
* Source IP, if applicable
* Event message
* Whether the event appeared centrally

This demonstrates the relationship between endpoint telemetry and SIEM data.

# 28. Basic Troubleshooting

## Problem 1 — Wazuh Agent Does Not Start

Check:

```bash
sudo systemctl status wazuh-agent
```

Then inspect:

```bash
sudo tail -n 50 /var/ossec/logs/ossec.log
```

Check the configuration file for mistakes:

```text
/var/ossec/etc/ossec.conf
```

---

## Problem 2 — Authentication Events Are Not Visible

Check:

```bash
sudo tail -n 20 /var/log/auth.log
```

Also check:

```bash
sudo journalctl --since "10 minutes ago"
```

If SSH is being tested, verify:

```bash
systemctl status ssh
```

---

## Problem 3 — System Log Is Not Updating

Check:

```bash
sudo tail -n 20 /var/log/syslog
```

Then inspect:

```bash
sudo journalctl --since "10 minutes ago"
```

The journal may still contain useful events even when a specific log file does not contain the expected message.

---

## Problem 4 — Wazuh Does Not Show the Event

First confirm that the event exists locally.

```text
Ubuntu Local Log
        ↓
Event Exists?
        ↓
YES
        ↓
Check Wazuh Agent
        ↓
Check Wazuh Server
        ↓
Check Dashboard
```

Do not troubleshoot the central dashboard first if the endpoint itself is not generating the expected event.

# 29. Safety and Authorization

All monitoring and event-generation activities must be performed only within the authorized home laboratory.

The following activities are permitted for this lab:

* Monitoring the user's own Ubuntu VM
* Testing the user's own SSH service
* Generating controlled failed authentication events
* Generating normal successful authentication events
* Running harmless `sudo` commands
* Observing system and process activity

Do not test authentication or monitoring controls against systems without authorization.

# Log Collection

## 1. Purpose

This document explains how security-relevant Linux logs are collected from the Ubuntu 22.04 LTS endpoint and forwarded to the central Wazuh monitoring system.

The objective is to understand:

* What log collection means
* Why centralized log collection is important
* Which Linux log sources are collected
* How the Wazuh Agent participates in collection
* How Linux logs move from the endpoint to the Wazuh Server
* How to verify that collection is working
* How to troubleshoot basic collection problems
* How to capture evidence of successful log collection

This stage focuses on **Log Collection**.

Detection rules and alert analysis are covered in later documentation.

---

# 2. Log Collection Concept

Log collection is the process of obtaining security-relevant log data from an endpoint and sending it to a centralized monitoring system.

In this lab:

```text id="qk6f8m"
Ubuntu 22.04 LTS
        ↓
Local Linux Logs
        ↓
Wazuh Agent
        ↓
Wazuh Server
        ↓
Centralized Security Data
```

The Wazuh Agent acts as the endpoint-side collection component.

---

# 3. Why Centralized Log Collection Matters

If logs remain only on individual endpoints, a SOC analyst would need to investigate each system separately.

Centralized collection provides a single monitoring location.

For example:

```text id="4f7h0b"
Ubuntu VM ──────┐
Windows VM ─────┼──→ Wazuh Server
Other Hosts ────┘
```

This allows security analysts to work with events from multiple monitored systems.

Centralized logs can help with:

* Security monitoring
* Event investigation
* Incident detection
* Timeline creation
* Correlation of activity
* Alert analysis
* Incident response

---

# 4. Log Collection vs Detection

These two concepts are different.

## Log Collection

Collection answers:

> "Did we receive the event data?"

Example:

```text id="n6j7b8"
Failed SSH Login
      ↓
auth.log
      ↓
Wazuh Agent
      ↓
Wazuh Server
```

## Detection

Detection answers:

> "Does this event or group of events indicate suspicious activity?"

Example:

```text id="0d9k2s"
Multiple Failed SSH Logins
          ↓
Detection Rule
          ↓
Security Alert
```

Therefore:

```text id="s3q2ae"
Event
  ↓
Log
  ↓
Collection
  ↓
Detection
  ↓
Alert
```

This lab stage concentrates on the **Collection** step.

# 6. Authentication Log Collection

The primary authentication log is:

```text id="2f1q7n"
/var/log/auth.log
```

It can contain events related to:

* SSH authentication
* Failed login attempts
* Successful login attempts
* `sudo` activity
* Authentication-related services

Example local event:

```text id="6p3y8d"
Failed password for testuser from 192.168.56.20
```

The actual format may differ depending on the authentication configuration.

The collection path is:

```text id="1a2v6c"

        ↓
/var/log/auth.log
        ↓
Wazuh Agent
        ↓
Wazuh Server
```

# 8. Wazuh Agent Role

The Wazuh Agent runs on the Ubuntu endpoint.

Its simplified role is:

```text id="g4h7e2"
Linux Endpoint
      ↓
Read Configured Log Sources
      ↓
Collect Log Events
      ↓
Send Telemetry
      ↓
Wazuh Server
```

The agent configuration file is:

```text id="b5t8n1"
/var/ossec/etc/ossec.conf
```

The agent service can be checked using:

```bash id="2x5m9p"
sudo systemctl status wazuh-agent
```

---

# 9. Basic Collection Configuration

Wazuh can monitor Linux log files using `localfile` configuration entries.

For the authentication log:

```xml id="8m2q4v"
<localfile>
  <location>/var/log/auth.log</location>
  <log_format>syslog</log_format>
</localfile>
```

For the system log:

```xml id="5w9c3r"
<localfile>
  <location>/var/log/syslog</location>
  <log_format>syslog</log_format>
</localfile>
```

These entries identify the local log files that the Wazuh Agent should monitor.

The configuration belongs inside:

```text id="r7f3k2"
/var/ossec/etc/ossec.conf
```

Do not add duplicate entries if these sources are already configured.

---

# 10. Check Existing Collection Configuration

Before changing the Wazuh configuration, inspect the existing configuration.

Run:

```bash id="v8n2j6"
sudo grep -n -A4 -B2 "auth.log" /var/ossec/etc/ossec.conf
```

Then:

```bash id="k4p9s1"
sudo grep -n -A4 -B2 "syslog" /var/ossec/etc/ossec.conf
```

If the expected entries already exist, do not create another copy.

You can also inspect the complete configuration:

```bash id="c6m1z8"
sudo less /var/ossec/etc/ossec.conf
```

---

# 11. Configuration Backup

Before making any changes, create a backup:

```bash id="t2x7q5"
sudo cp /var/ossec/etc/ossec.conf /var/ossec/etc/ossec.conf.backup
```

Verify the backup:

```bash id="m5r8v2"
sudo ls -l /var/ossec/etc/ossec.conf*
```

The backup provides a simple recovery option if an incorrect configuration is introduced.

---

# 12. Authentication Log Collection Setup

If `/var/log/auth.log` is not already configured, add the following inside the appropriate `<ossec_config>` section:

```xml id="j9k3w7"
<localfile>
  <location>/var/log/auth.log</location>
  <log_format>syslog</log_format>
</localfile>
```

Save the configuration.

Then restart the Wazuh Agent:

```bash id="e5q1n8"
sudo systemctl restart wazuh-agent
```

# 14. Verify Wazuh Agent Status

After configuration changes, check:

```bash id="q6t1p9"
sudo systemctl status wazuh-agent
```

The service should be active.

A simplified expected state is:

```text id="y3r8m6"
wazuh-agent
     ↓
   ACTIVE
```

If the service fails to start, do not continue with collection testing until the configuration problem is investigated.

# 15. Check Wazuh Agent Logs

The Wazuh Agent log is:

```text id="u7p2d4"
/var/ossec/logs/ossec.log
```

View recent entries:

```bash id="k9f4s3"
sudo tail -n 50 /var/ossec/logs/ossec.log
```

This can help identify problems such as:

* Configuration errors
* Connection problems
* Permission problems
* Agent startup problems
* Collection-related errors

---

# 16. Verify Local Log Generation

Before testing centralized collection, confirm that the endpoint is actually generating logs.

Check authentication logs:

```bash id="r2x6m8"
sudo tail -n 20 /var/log/auth.log
```

Check system logs:

```bash id="v5k9c1"
sudo tail -n 20 /var/log/syslog
```

If the endpoint is not generating the expected event locally, the problem may not be related to Wazuh collection.

---

# 17. Controlled Authentication Test

A controlled authentication event can be used to test collection.

From an authorized lab machine, perform one failed SSH login attempt against the Ubuntu VM using an intentionally incorrect password.

Do this only against the authorized lab endpoint.

Then check locally:

```bash id="n4h8q2"
sudo grep "Failed password" /var/log/auth.log
```

Expected flow:

```text id="f6m2r9"
Controlled SSH Attempt
        ↓
Authentication Event
        ↓
/var/log/auth.log
        ↓
Wazuh Agent
```

---

# 18. Controlled Successful Authentication Test

Perform a normal authorized SSH login to the Ubuntu VM.

Then check:

```bash id="w3q7k5"

```

Expected flow:

```text id="h8p1v4"
Successful SSH Login
        ↓
Authentication Event
        ↓
/var/log/auth.log
        ↓

```

# 19. Controlled Sudo Test

Run a harmless command:

```bash id="m7c3x9"
sudo whoami
```

Expected output:

```text id="b2k6v8"
root
```

Then check:

```bash id="q5n1s7"

```

If the event is recorded locally, it can be used to test centralized collection.

# 22. Collection Validation Procedure

Perform validation in the following order.

### Step 1 — Confirm the local source

```bash id="v6m2k8"
sudo tail -n 20 /var/log/auth.log
```

### Step 2 — Generate a controlled event

Perform one authorized test activity.

### Step 3 — Confirm local event

Search:

```bash id="p3x7n1"
sudo grep "Failed password" /var/log/auth.log
```

or use the appropriate search for the event generated.

### Step 4 — Check the Wazuh Agent

```bash id="r8c4m6"
sudo systemctl status wazuh-agent
```

### Step 5 — Check the agent log

```bash id="j2v9q5"
sudo tail -n 50 /var/ossec/logs/ossec.log
```

### Step 6 — Check the Wazuh Dashboard

Search for the corresponding event.

### Step 7 — Compare the events

Confirm that the centrally collected event corresponds to the local event.

# 24. Understanding Collection Failures

A collection problem can occur at different points.

```text id="w5n2j8"
Event Generated?
       │
       ├── NO → Check Linux activity/logging
       │
       └── YES
            ↓
       Log Contains Event?
            │
            ├── NO → Check local logging
            │
            └── YES
                 ↓
          Wazuh Agent Running?
                 │
                 ├── NO → Check agent
                 │
                 └── YES
                      ↓
              Event Reaches Server?
                      │
                      ├── NO → Check agent/server connection
                      │
                      └── YES
                           ↓
                       Dashboard
```

This basic troubleshooting model helps identify where the problem exists.

# 25. Basic Troubleshooting

## Problem 1 — Log File Does Not Exist

Check:

```bash id="m8q4t6"
ls -l /var/log/
```

Then check the journal:

```bash id="y2v7k9"
sudo journalctl --since "10 minutes ago"
```

Logging configuration may differ depending on the system.

---

## Problem 2 — Wazuh Agent Is Inactive

Check:

```bash id="p6x3n8"
sudo systemctl status wazuh-agent
```

Then:

```bash id="c9r2m5"
sudo tail -n 50 /var/ossec/logs/ossec.log
```

---

## Problem 3 — Agent Fails After Configuration Change

Restore the backup if necessary:

```bash id="h4v8q1"
sudo cp /var/ossec/etc/ossec.conf.backup /var/ossec/etc/ossec.conf
```

Then restart:

```bash id="s7m3k9"
sudo systemctl restart wazuh-agent
```

Check the status again.

---

## Problem 4 — Local Event Exists but Wazuh Does Not Show It

Follow this sequence:

```text id="d2f6w8"
Local Log
   ↓
Agent Status
   ↓
Agent Log
   ↓
Wazuh Server
   ↓
Dashboard
```

First verify that the event exists locally.

Do not assume that a missing dashboard event means the Linux endpoint failed to generate the event.

---

## Problem 5 — Too Many Events

During testing, avoid generating unnecessary large amounts of activity.

Use targeted searches such as:

```bash id="x8m2q5"
sudo grep "Failed password" /var/log/auth.log
```

or limit journal output:

```bash id="k6p4v9"
sudo journalctl --since "10 minutes ago"
```

# 28. Security and Authorization

All log-collection testing must be performed only on authorized systems.

The following activities are acceptable within this home lab:

* Reading local Linux logs
* Monitoring the user's own Ubuntu VM
* Generating controlled authentication events
* Performing authorized SSH login tests
* Running harmless sudo commands
* Verifying Wazuh collection

Do not generate authentication attacks or excessive traffic against external systems.

# 30. SOC Learning Outcome

After completing this stage, the learner should be able to explain:

> How a security event generated on a Linux endpoint becomes centralized security telemetry.

The complete process is:

```text id="q8m3v6"
User / System Activity
          ↓
       Event
          ↓
     Linux Logging
          ↓
      Local Log
          ↓
     Wazuh Agent
          ↓
    Wazuh Server
          ↓
 Centralized Telemetry
```

The learner should also understand that **collection alone does not mean detection**.

A collected event becomes useful for security monitoring when it can be analyzed and evaluated by detection logic.

# Alert Analysis

## 1. Purpose

This document explains how a SOC analyst analyzes security alerts generated by Wazuh during the Linux Security Monitoring Lab.

The objective is to understand:

* What a security alert represents
* The difference between an event and an alert
* How to perform basic alert triage
* How to examine Wazuh alert information
* How to validate whether an alert represents real activity
* How to correlate an alert with Linux logs
* How to classify alerts
* How to build a basic event timeline
* How to document an alert investigation
* How to identify false positives
* How to determine whether further investigation is required

This stage focuses on **beginner-level alert analysis and SOC triage**.

Advanced threat hunting, forensic analysis, and automated response are outside the scope of this document.

---

# 2. What Is an Alert?

A security alert is a notification generated when monitored activity matches a detection condition.

Simplified flow:

```
Linux Activity
      ↓
    Event
      ↓
   Log
      ↓
 Wazuh Agent
      ↓
 Wazuh Server
      ↓
Detection Rule
      ↓
    Alert
      ↓
 SOC Analyst
```

An alert tells the analyst:

> Something happened that may require investigation.

An alert does **not** automatically mean:

> An attack definitely occurred.

The analyst must examine the available evidence.

---

# 3. Alert vs Event

These two concepts must be clearly understood.

## Event

An event is an activity that occurs on the system.

Example:

```
User attempted SSH login
```

## Log

The system records the event in a log.

Example:

```
/var/log/auth.log
```

## Alert

Wazuh identifies activity that matches a detection condition and presents it as an alert.

Example:

```
Authentication-related alert
```

Therefore:

```
Event
  ↓
Log
  ↓
Collection
  ↓
Detection
  ↓
Alert
```

---

# 4. Why Alert Analysis Matters in a SOC

A SOC may receive many alerts.

The analyst must determine:

* What happened?
* When did it happen?
* Which system was affected?
* Which user was involved?
* Where did the activity originate?
* Was the activity expected?
* Is there related activity?
* Does the alert require escalation?

Without analysis:

```
Alert
  ↓
Immediate Assumption
  ↓
Incorrect Decision
```

With analysis:

```
Alert
  ↓
Validate
  ↓
Investigate
  ↓
Understand Context
  ↓
Classify
  ↓
Document
  ↓
Respond / Escalate if Required
```

---

# 5. Basic Alert Analysis Workflow

The beginner SOC alert-analysis workflow is:

```
Alert Received
      ↓
Validate Alert
      ↓
Identify Endpoint
      ↓
Check Timestamp
      ↓
Review User / Source
      ↓
Review Event Details
      ↓
Check Related Events
      ↓
Correlate With Local Logs
      ↓
Determine Context
      ↓
Classify Alert
      ↓
Document Findings
      ↓
Escalate / Respond if Required
```

This workflow should be followed consistently.

# 7. Basic Wazuh Alert Information

When opening an alert in the Wazuh Dashboard, review the information available for that alert.

Important information may include:

* Timestamp
* Agent name
* Agent ID
* Rule ID
* Rule description
* Rule level/severity
* Source IP
* Destination information, if available
* Username
* Event source
* Decoder information
* Full log/event data
* MITRE ATT&CK information, if available

The exact fields displayed can vary depending on the Wazuh version and the event being analyzed.

Do not assume that every alert will contain every field.

---

# 8. First Question — What Happened?

The first question during alert analysis is:

> What actually happened?

Read the alert description and event information.

For example:

```
Failed SSH Authentication
```

could mean:

```
User
  ↓
SSH Login Attempt
  ↓
Incorrect Authentication
  ↓
Authentication Failure
```

Do not immediately classify this as an attack.

First understand the actual event.

---

# 9. Second Question — When Did It Happen?

Check the alert timestamp.

Record:

* Date
* Time
* Time zone if available

Example:

```
Alert Time:
2026-XX-XX 10:25:31
```

Then compare the time with the Linux log.

For example:

```
Wazuh Alert
     ↓
10:25:31

Linux auth.log
     ↓
10:25:31
```

A matching timestamp increases confidence that the alert corresponds to the event being investigated.

---

# 10. Third Question — Which Endpoint Was Involved?

Identify the Wazuh agent that generated the alert.

For this lab, the primary endpoint is:

```
Ubuntu 22.04 LTS
```

Confirm that the alert belongs to the expected endpoint.

This prevents confusion when multiple virtual machines are connected to the same Wazuh server.

---

# 11. Fourth Question — Which User Was Involved?

If available, identify the user associated with the event.

For example:

```
Username: parijat
```

or:

```
Username: testuser
```

Then ask:

* Is the account authorized?
* Is the account expected on this system?
* Was the account supposed to perform the activity?
* Was the account involved in previous related events?

A username alone does not determine whether activity is malicious.

Context is required.

---

# 12. Fifth Question — What Is the Source?

For network-related events, identify the source IP if available.

Example:

```
Source IP:
192.168.XX.XX
```

Ask:

* Is the source inside the home lab?
* Is it the expected testing machine?
* Is the source associated with the user?
* Is the source unexpected?

For SSH testing, the source may be another authorized virtual machine.

---

# 13. Sixth Question — What Process or Command Was Involved?

For process or shell-related alerts, inspect the available process or command information.

Look for:

* Process name
* Command
* User
* Parent process, if available
* Time
* Related activity

For example:

```
User
  ↓
sudo
  ↓
Command
  ↓
System Activity
```

Do not automatically classify a command as malicious simply because it is unfamiliar.

---

# 14. Seventh Question — Was the Activity Expected?

This is one of the most important SOC questions.

Ask:

> Was this activity expected in the environment?

Example:

```
sudo Activity
     ↓
Authorized Lab Administrator
     ↓
Planned Testing
     ↓
Expected Activity
```

Another example:

```
SSH Login
     ↓
Unknown Source
     ↓
Unexpected Account
     ↓
Requires Investigation
```

Context determines priority.

---

# 15. Severity vs Priority

These concepts should not be confused.

## Severity

Severity is associated with the detection or alert.

It helps indicate how significant the detected activity may be according to the detection logic.

## Priority

Priority is determined by the analyst using context.

For example:

```
Medium-Severity Alert
        +
Critical Server
        +
Unknown Account
        ↓
   Higher Priority
```

Therefore:

> Alert severity and investigation priority are not always the same thing.

---

# 16. Basic Alert Triage Questions

Use these questions during every alert investigation:

1. What happened?
2. When did it happen?
3. Which endpoint was involved?
4. Which account was involved?
5. What was the source IP?
6. What process or command was involved?
7. Was the activity expected?
8. What happened immediately before the alert?
9. What happened immediately after the alert?
10. Are there related alerts?
11. Does the local Linux log confirm the event?
12. Is there enough evidence to classify the activity?

These questions form the basic SOC analyst mindset.

# 17. Exact Wazuh Alert Validation

Before analyzing an alert, confirm that it actually corresponds to the event generated in the lab.

## Step 1 — Confirm the Agent

On Ubuntu:

```
sudo systemctl is-active wazuh-agent
```

Expected:

```
active
```

---

## Step 2 — Confirm the Local Event

For an SSH authentication event:

```
sudo grep "Failed password" /var/log/auth.log
```

For successful authentication:

```
sudo grep "Accepted" /var/log/auth.log
```

For sudo activity:

```
sudo grep "sudo:" /var/log/auth.log
```

---

## Step 3 — Open Wazuh Dashboard

Open the Wazuh Dashboard used by the home lab.

Open the available alert/event monitoring view.

---

## Step 4 — Select the Correct Agent

Filter the available results to the Ubuntu 22.04 LTS agent.

This prevents unrelated events from other lab systems from affecting the investigation.

---

## Step 5 — Select the Correct Time Range

Use a time range that contains the event.

For recent testing:

```
Last 15 minutes
```

can be used.

Adjust the time range if the event occurred earlier.

---

## Step 6 — Locate the Alert

Search/filter for information associated with the test.

Examples:

```
Failed password
Accepted
sudo
SSH
Authentication
```

The exact alert wording may differ.

---

## Step 7 — Open Alert Details

Record the available information:

```
Timestamp
Agent
Rule ID
Rule Description
Rule Level
Source IP
Username
Event Data
```

Only record fields that are actually present.

---

## Step 8 — Compare With Local Evidence

Compare the Wazuh alert with:

```
/var/log/auth.log
```

or the relevant journal entry.

Check:

* Timestamp
* Username
* Source
* Event description
* Authentication result

If the information matches, the alert has been successfully validated against endpoint evidence.

---

# 18. Local Log Correlation

Local Linux logs are useful for validating Wazuh alerts.

Useful commands include:

```
sudo tail -n 50 /var/log/auth.log

sudo journalctl --since "10 minutes ago"

sudo grep "Failed password" /var/log/auth.log

sudo grep "Accepted" /var/log/auth.log

sudo grep "sudo:" /var/log/auth.log
```

The objective is:

```
Wazuh Alert
      ↓
Identify Event
      ↓
Check Local Log
      ↓
Compare Evidence
      ↓
Confirm Context
```

# 19. Alert Analysis Example 1 — Failed SSH Authentication

## Alert

Suppose Wazuh generates an authentication-related alert.

Initial information:

```
Event:
Failed SSH Authentication
```

The analyst should check:

* Timestamp
* Username
* Source IP
* Number of failures
* Previous authentication events
* Subsequent authentication events

Possible timeline:

```
10:20:01  Failed SSH Login
10:20:05  Failed SSH Login
10:20:12  Failed SSH Login
```

This may require more attention than one isolated failed login.

However, the analyst must still determine whether the activity was part of an authorized test.

---

# 20. Alert Analysis Example 2 — Failed Login Followed by Success

A more interesting sequence is:

```
10:20:01  Failed SSH Login
10:20:05  Failed SSH Login
10:20:12  Successful SSH Login
10:21:02  sudo Activity
```

This sequence should be investigated as a related event chain.

The analyst should ask:

* Was the successful login expected?
* Was the account authorized?
* Was the source IP expected?
* Did the same source generate the failures?
* Was the `sudo` activity authorized?

The individual alerts may not tell the complete story.

The timeline provides additional context.

---

# 21. Alert Analysis Example 3 — Sudo Activity

Suppose an alert is related to privileged activity.

Check:

```
sudo grep "sudo:" /var/log/auth.log
```

Then determine:

* Which user executed `sudo`
* When it occurred
* What command was executed, if recorded
* Whether the user was authorized
* Whether the activity was part of the lab test

Example:

```
Authorized User
      ↓
sudo whoami
      ↓
Planned Lab Test
      ↓
Expected Activity
```

This may be classified as benign or expected activity.

---

# 22. Alert Analysis Example 4 — Suspicious Process

Suppose an alert indicates unusual process activity.

The analyst should examine:

* Process name
* User
* Command
* Time
* Parent process, if available
* Related alerts
* Recent authentication activity

Example investigation:

```
Suspicious Process
       ↓
Who Started It?
       ↓
When?
       ↓
Which Command?
       ↓
Was Login Activity Related?
       ↓
Expected or Unexpected?
       ↓
Classification
```

Do not classify a process as malicious without sufficient evidence.

# 23. Building a Basic Timeline

A timeline helps organize multiple events.

Example:

| Time     | Event                | Source      | User     | Significance              |
| -------- | -------------------- | ----------- | -------- | ------------------------- |
| 10:20:01 | Failed SSH login     | 192.168.X.X | testuser | Authentication failure    |
| 10:20:05 | Failed SSH login     | 192.168.X.X | testuser | Related failure           |
| 10:20:12 | Successful SSH login | 192.168.X.X | testuser | Successful authentication |
| 10:21:02 | sudo activity        | Local       | testuser | Privilege activity        |

The timeline allows the analyst to see relationships between events.

# 24. Alert Classification

After analysis, classify the alert based on available evidence.

Basic categories:

### Benign

The activity is legitimate and expected.

Example:

```
Planned Lab Test
      ↓
   Expected
      ↓
     Benign
```

### Suspicious

The activity is unusual or unexpected, but there is not enough evidence to confirm malicious activity.

Example:

```
Unexpected Login
      ↓
Limited Evidence
      ↓
   Suspicious
```

### Malicious

There is sufficient evidence to determine that the activity is malicious.

This classification should be used carefully.

Do not label an event malicious simply because it looks unusual.

### False Positive

The alert was generated, but the underlying activity was legitimate.

Example:

```
Alert
  ↓
Investigation
  ↓
Authorized Administrator
  ↓
False Positive
```

---

# 25. Classification Decision Flow

Use this simple decision process:

```
Alert
  ↓
Validate Event
  ↓
Is Activity Expected?
  ↓
┌───────────────┐
│               │
```

YES              NO
│               │
↓               ↓
Benign       Investigate Further
↓
Sufficient Evidence?
/          
NO            YES
↓              ↓
Suspicious       Malicious

```

The classification should always be supported by evidence.

---

# 26. Checking Related Alerts

A single alert may not be enough.

Look for related activity around the same time.

For example:

    Authentication Failure
            ↓
       Successful Login
            ↓
         sudo Activity
            ↓
       Process Activity

This can provide more useful context than analyzing each event separately.

At the beginner level, focus on simple chronological correlation.

# 30. False Positive Handling

A false positive should not simply be ignored.

The analyst should document why the alert was considered benign.

Example:

    Alert
      ↓
    Investigation
      ↓
    Authorized User
      ↓
    Planned Activity
      ↓
    False Positive
      ↓
    Document Reason

This helps improve future alert analysis.

---

# 31. When an Alert Requires Escalation

In a real SOC, an alert may require escalation when:

- Activity is unexpected
- A privileged account is involved
- Multiple related suspicious events exist
- Authentication and process activity are connected
- The affected endpoint is important
- Evidence suggests compromise
- The analyst cannot safely determine the cause

For this home lab, escalation can be simulated through documentation.

Example:

    Alert
      ↓
    Analysis
      ↓
    Suspicious
      ↓
    Escalation Required
      ↓
    Incident Report

# 34. Basic Troubleshooting

## Problem 1 — Alert Cannot Be Found

Check:

- Correct agent
- Correct time range
- Correct event type
- Dashboard filters

Then check the local Linux log.

---

## Problem 2 — Alert Exists but Details Are Limited

Use the available event/log information.

Then correlate with:

    /var/log/auth.log

or:

    sudo journalctl --since "10 minutes ago"

Do not invent missing information.

---

## Problem 3 — Local Log Exists but Alert Is Missing

Review:

    sudo systemctl status wazuh-agent

Then:

    sudo tail -n 50 /var/ossec/logs/ossec.log

Confirm that the relevant log source is configured for collection.

---

## Problem 4 — Alert Looks Suspicious but Evidence Is Limited

Do not immediately classify it as malicious.

Use:

    Suspicious
        ↓
    Gather More Evidence
        ↓
    Reassess
```

# Windows Event Logging

## Purpose

Windows Event Logging provides the foundational security telemetry required for endpoint monitoring and incident investigation.

This document explains the Windows event logging system, important event sources, security-relevant Event IDs, and how analysts can use Windows logs to understand endpoint activity.

---

## Windows Event Logging Overview

Windows continuously generates events when important system, user, application, and security activities occur.

These events can provide visibility into:

* User authentication
* Account activity
* Process execution
* Privilege changes
* System changes
* Application activity
* PowerShell execution
* Security policy changes
* Network-related activity
* File and service activity

Security analysts use these events to establish what happened, when it happened, and which account or process was involved.

---

## Windows Event Logs

The primary Windows event logs include:

### Security

The Security log contains security-related events generated according to Windows auditing configuration.

Common activities include:

* Successful logons
* Failed logons
* Account management
* Privilege use
* Process-related auditing
* Security policy changes

---

### System

The System log contains events generated by Windows system components.

It can help identify:

* Service activity
* Driver events
* System startup and shutdown
* Hardware-related events
* System errors
* System configuration changes

---

### Application

The Application log contains events generated by applications and software components.

It can help investigate:

* Application errors
* Application crashes
* Software activity
* Application-specific security events

---

### PowerShell Logs

PowerShell can generate additional telemetry through its operational logging mechanisms.

Depending on configuration, useful information may include:

* PowerShell engine activity
* Script execution
* Command execution
* Script block content
* Module activity

PowerShell logging is particularly valuable when investigating suspicious administrative activity or script-based execution.

---

### Sysmon Logs

When Sysmon is installed and configured, it provides enhanced endpoint telemetry.

The primary Sysmon event channel is:

`Microsoft-Windows-Sysmon/Operational`

Sysmon can provide visibility into:

* Process creation
* Network connections
* File creation
* Driver loading
* Process access
* Registry activity
* DNS queries
* Other endpoint behaviors

Sysmon should be treated as an additional telemetry source rather than a replacement for native Windows logging.

---

## Windows Event Viewer

Windows Event Viewer provides a graphical interface for viewing Windows events.

Typical navigation:

`Event Viewer → Windows Logs → Security`

Other useful locations include:

`Event Viewer → Windows Logs → System`

`Event Viewer → Windows Logs → Application`

For Sysmon:

`Event Viewer → Applications and Services Logs → Microsoft → Windows → Sysmon → Operational`

The exact available channels depend on the installed components and logging configuration.

## Important Security Event IDs

The following Event IDs are particularly useful for entry-level SOC monitoring.

### Authentication Events

| Event ID | Description                              | Monitoring Value                        |
| -------- | ---------------------------------------- | --------------------------------------- |
| 4624     | Successful logon                         | Identify successful authentication      |
| 4625     | Failed logon                             | Detect repeated authentication failures |
| 4634     | Logoff                                   | Track session termination               |
| 4647     | User initiated logoff                    | Identify user-initiated logoff          |
| 4672     | Special privileges assigned to new logon | Identify privileged logon activity      |

---

### Account Management Events

| Event ID | Description             | Monitoring Value                      |
| -------- | ----------------------- | ------------------------------------- |
| 4720     | User account created    | Detect unexpected account creation    |
| 4722     | User account enabled    | Monitor account changes               |
| 4725     | User account disabled   | Monitor account changes               |
| 4726     | User account deleted    | Detect account deletion               |
| 4738     | User account changed    | Identify account modification         |
| 4740     | User account locked out | Investigate possible password attacks |

---

### Process and Execution Events

| Event ID | Description         | Monitoring Value              |
| -------- | ------------------- | ----------------------------- |
| 4688     | New process created | Investigate process execution |
| 4689     | Process exited      | Track process termination     |

Event 4688 becomes significantly more useful when command-line auditing is appropriately configured.

---

## PowerShell Event IDs

PowerShell-related events depend on the enabled logging configuration.

Important examples include:

| Event ID | Description               | Monitoring Value                                |
| -------- | ------------------------- | ----------------------------------------------- |
| 4103     | Module logging            | Provides module-level PowerShell activity       |
| 4104     | Script Block Logging      | Provides visibility into executed script blocks |
| 400      | PowerShell engine started | Identifies PowerShell session start             |
| 403      | PowerShell engine stopped | Identifies PowerShell session termination       |

Event 4104 can be particularly valuable during investigation because it may provide visibility into script content.

---

## Security Policy Events

Security policy changes may also generate useful telemetry.

Examples include:

* Audit policy changes
* Authentication policy changes
* Privilege assignment changes
* Security configuration modifications

These events can help identify unauthorized changes to the security posture of the endpoint.

## Event Structure

A Windows event contains multiple fields that analysts should examine.

Important fields include:

* Event ID
* Timestamp
* Computer
* User
* Account name
* Account domain
* Logon type
* Source address
* Process name
* Process ID
* Parent process
* Command line
* Authentication information
* Event description

Not every event contains every field.

## Event Analysis Model

When analyzing a Windows event, use the following questions:

1. **What happened?**
2. **When did it happen?**
3. **Which system generated the event?**
4. **Which user or account was involved?**
5. **Which process was involved?**
6. **What was the parent process?**
7. **What command line was executed?**
8. **What was the source of the activity?**
9. **Is the activity expected?**
10. **Does the event correlate with other events?**

This converts an individual event into meaningful security context.

---

## Authentication Monitoring

Authentication events should be analyzed as a sequence rather than individually.

Example:

```
Multiple 4625 events
        ↓
Repeated failed authentication
        ↓
Source/account identified
        ↓
4624 successful logon
        ↓
Authentication sequence investigated
```

A single failed login may be normal.

A large number of failures followed by a successful login may require further investigation.

---

## Process Monitoring

Process events provide visibility into endpoint execution.

For example:

```
User Activity
      ↓
Process Created
      ↓
Parent Process
      ↓
Command Line
      ↓
Child Process
      ↓
Network/File Activity
```

The analyst should examine the complete process context instead of judging a process only by its filename.

---

## PowerShell Monitoring

PowerShell is a legitimate administrative tool but can also be abused.

Monitoring should focus on:

* Unexpected PowerShell execution
* Unusual parent processes
* Suspicious command lines
* Encoded commands
* Script execution
* Unusual administrative activity
* PowerShell activity occurring alongside authentication or process anomalies

The presence of PowerShell alone does not indicate malicious activity.

---

## Event Correlation

Individual events often provide limited context.

Correlation improves investigation quality.

Example:

```
4625
Failed Logon
     ↓
4625
Failed Logon
     ↓
4624
Successful Logon
     ↓
4672
Privileged Logon
     ↓
4688
New Process
     ↓
PowerShell Activity
     ↓
Investigation
```

This sequence provides substantially more context than analyzing any single event.

## Baseline Monitoring

Before investigating suspicious behavior, establish a baseline of normal activity.

Examples:

* Normal user logons
* Normal administrative activity
* Common process executions
* Normal PowerShell usage
* Regular system events
* Expected service activity

A baseline helps analysts identify deviations from normal behavior.

## Practical Exercise

Perform the following controlled exercise:

1. Log in to the Windows endpoint.
2. Open Event Viewer.
3. Navigate to the Security log.
4. Identify a successful logon event.
5. Record the Event ID and timestamp.
6. Examine the user/account information.
7. Generate a controlled failed authentication event.
8. Locate the corresponding security event.
9. Compare the successful and failed authentication events.
10. Record relevant evidence.
11. Repeat the process using a controlled process or PowerShell activity.
12. Compare the resulting telemetry.

The objective is to become comfortable moving from an observed action to its corresponding Windows security telemetry.

* Event log service status
* Correct event channel
* Logging configuration
* PowerShell logging configuration
* Sysmon installation/configuration
* Wazuh agent status
* Log collection configuration
* Event filtering

## Conclusion

Windows Event Logging provides the telemetry foundation for endpoint security monitoring.

Effective SOC analysis requires more than identifying an Event ID.

The analyst should understand the event's:

**Time → User → System → Process → Command Line → Source → Context → Related Events**

This contextual approach allows Windows events to be transformed into actionable security information.

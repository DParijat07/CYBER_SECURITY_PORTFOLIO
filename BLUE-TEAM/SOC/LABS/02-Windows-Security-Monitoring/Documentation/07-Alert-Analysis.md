# Alert Analysis

## Purpose

The purpose of this document is to explain how SOC analysts analyze security alerts generated from Windows endpoint telemetry.

Alert analysis is the process of determining whether an alert represents:

* Benign activity
* Expected administrative activity
* A false positive
* Suspicious activity
* A potential security incident

The objective is to move from a raw alert to a clear, evidence-based analyst decision.

---

# Alert Analysis Workflow

The Windows Security Monitoring Lab follows this workflow:

```
Detection Rule
      ↓
    Alert
      ↓
Alert Triage
      ↓
Context Collection
      ↓
Event Correlation
      ↓
Investigation
      ↓
Analyst Decision
   ↙       ↘
Benign    Suspicious
   ↓         ↓
Close     Escalate
             ↓
          Response
```

Alert analysis should be based on available evidence rather than assumptions.

# Wazuh Investigation Steps

Once an alert is generated, the analyst should use Wazuh to investigate the event systematically.

The investigation workflow is:

```
Wazuh Alert
     ↓
Identify Alert
     ↓
Review Rule
     ↓
Review Event Fields
     ↓
Identify Host/User
     ↓
Examine Timestamp
     ↓
Search Related Events
     ↓
Build Timeline
     ↓
Assess Context
     ↓
Determine Severity
     ↓
Analyst Decision
   ↙       ↘
Benign    Suspicious
   ↓         ↓
 Close    Escalate
```

---

## Step 1 — Open the Wazuh Dashboard

Access the Wazuh dashboard used by the lab.

Navigate to the area used for security alerts and event analysis.

The objective is to locate the alert generated by the Windows monitoring endpoint.

Verify:

* Alert time
* Alert source
* Agent/endpoint
* Rule
* Severity

---

## Step 2 — Locate the Alert

Search for the relevant alert using available fields such as:

* Rule ID
* Event ID
* Agent name
* Hostname
* Username
* Source IP
* Time range
* Alert description

Example:

```
Rule ID: 100101
Event ID: 4625
Agent: Windows-Monitoring-VM
```

The exact search method may vary depending on the Wazuh dashboard version and configuration.

---

## Step 3 — Review Alert Summary

First review the alert without immediately making a conclusion.

Record:

* Alert timestamp
* Alert level
* Rule ID
* Rule description
* Agent name
* Hostname
* Event ID
* Event channel
* Detection category

The first objective is to understand **why Wazuh generated the alert**.

---

## Step 4 — Inspect the Full Event

Open the alert's detailed event information.

Review the available fields.

Important fields may include:

* `timestamp`
* `agent`
* `rule`
* `win.system.eventID`
* `win.system.providerName`
* `win.system.channel`
* `win.eventdata.targetUserName`
* `win.eventdata.subjectUserName`
* `win.eventdata.ipAddress`
* `win.eventdata.commandLine`
* `win.eventdata.newProcessName`
* `win.eventdata.parentProcessName`

Not every field will be present for every Windows event.

The analyst should work with the fields actually available in the collected telemetry.

---

## Step 5 — Identify the Affected Endpoint

Determine which endpoint generated the alert.

Record:

* Agent name
* Hostname
* IP address where available
* Operating system
* Asset role where known

Example:

```
Alert
  ↓
Agent: Windows-Monitoring-VM
  ↓
Host: Windows Endpoint
  ↓
Investigate Endpoint Activity
```

This establishes the scope of the investigation.

---

## Step 6 — Identify the User

Determine which account is associated with the activity.

Review:

* Target username
* Subject username
* Account name
* Domain
* User context
* Privilege level where available

Ask:

> Is this user expected to perform this activity?

An administrator account performing administrative maintenance should be interpreted differently from an unexpected account performing the same activity.

---

## Step 7 — Review the Rule

Identify the Wazuh rule that generated the alert.

Review:

* Rule ID
* Rule level
* Rule description
* Rule groups
* Detection condition
* MITRE ATT&CK mapping where available

Example:

```
Alert
  ↓
Rule ID 100101
  ↓
Repeated Failed Logons
  ↓
Event ID 4625
  ↓
Investigate Authentication Activity
```

Understanding the rule prevents the analyst from investigating the wrong behavior.

---

## Step 8 — Review the Event ID

Identify the underlying Windows Event ID.

Examples:

* `4624` — Successful logon
* `4625` — Failed logon
* `4672` — Special privileges assigned
* `4688` — Process creation
* `4720` — User account created
* `4738` — User account changed
* `4740` — Account locked out
* `4104` — PowerShell Script Block Logging

The Event ID provides the starting point for understanding the activity.

---

## Step 9 — Review the Timestamp

Check the exact event timestamp.

Determine:

* When the activity occurred
* Whether multiple events occurred close together
* Whether the activity happened during expected activity periods
* Whether events before and after the alert are relevant

Do not rely only on the alert timestamp when reconstructing an incident timeline.

---

## Step 10 — Search Related Events

The original alert should be treated as the starting point of the investigation.

Search for related events involving:

* Same host
* Same user
* Same source IP
* Same process
* Same Event ID
* Same time window

Example:

```
Initial Alert
     ↓
Search ± Time Window
     ↓
Related Authentication Events
     ↓
Related Process Events
     ↓
Related PowerShell Events
     ↓
Build Context
```

This helps determine whether the alert is isolated or part of a larger sequence.

---

## Step 11 — Investigate Authentication Activity

For authentication alerts, search for related:

* `4625` — Failed logon
* `4624` — Successful logon
* `4634` — Logoff
* `4672` — Privileged logon
* `4740` — Account lockout

Example:

```
4625
Failed Logon
   ↓
4625
   ↓
4625
   ↓
4624
Successful Logon
   ↓
4672
Privileged Logon
```

This sequence would require more investigation than a single isolated failed logon.

---

## Step 12 — Investigate Process Activity

For process-related alerts, review available process information.

Look for:

* Process name
* Process path
* Process ID
* Parent process
* Command line
* User
* Creation time

Example:

```
Process Alert
     ↓
Identify Process
     ↓
Identify Parent
     ↓
Review Command Line
     ↓
Identify User
     ↓
Search Related Events
```

If Sysmon is available, use its additional process telemetry to enrich the investigation.

---

## Step 13 — Investigate PowerShell Activity

For PowerShell-related alerts, search for:

* PowerShell execution
* Script Block Logging
* Module logging
* Parent process
* User
* Command line
* Related process activity
* Related network activity

Particular attention should be given to suspicious characteristics such as:

* Encoded commands
* Obfuscation
* Unexpected execution
* Unusual parent-child relationships
* Unexpected users
* Download or remote-execution behavior

PowerShell itself is not evidence of malicious activity.

---

## Step 14 — Investigate Account Activity

For account-related alerts, investigate:

* Account creation
* Account modification
* Account lockout
* Privilege changes
* Group membership changes where telemetry is available

Relevant events include:

* `4720`
* `4738`
* `4740`

Determine:

> Who performed the action, which account was affected, when it occurred, and whether it was authorized?

---

## Step 15 — Build an Event Timeline

Organize important events chronologically.

Example:

| Time     | Event | User  | Activity         |
| -------- | ----: | ----- | ---------------- |
| 10:01:12 |  4625 | user1 | Failed logon     |
| 10:01:15 |  4625 | user1 | Failed logon     |
| 10:01:19 |  4625 | user1 | Failed logon     |
| 10:01:31 |  4624 | user1 | Successful logon |
| 10:01:35 |  4672 | user1 | Privileged logon |
| 10:01:42 |  4688 | user1 | Process created  |

The timeline helps identify relationships between events.

---

## Step 16 — Compare Against the Baseline

Determine whether the observed behavior is normal for the lab environment.

Compare:

* User behavior
* Process activity
* Authentication patterns
* PowerShell usage
* Account activity
* Source addresses
* Time of activity

Baseline comparison helps reduce false positives.

---

## Step 17 — Assess the Alert

After gathering context, classify the alert.

Possible classifications:

### Benign

The activity is expected and authorized.

### False Positive

The detection logic triggered, but the activity is not security-relevant.

### Suspicious

The activity cannot be confidently explained and requires further investigation.

### Confirmed Incident

Evidence indicates malicious or unauthorized activity requiring incident response.

---

## Step 18 — Determine Escalation

Escalate when evidence indicates potentially malicious activity.

Escalation may be appropriate when there is:

* Unauthorized authentication
* Successful authentication after suspicious failures
* Suspicious privileged activity
* Suspicious process execution
* Suspicious PowerShell activity
* Unauthorized account creation
* Multiple correlated alerts
* Evidence of persistence or lateral movement

The escalation decision should include supporting evidence.

---

## Step 19 — Document the Investigation

Record:

* Alert ID/reference
* Rule ID
* Event ID
* Severity
* Host
* User
* Source
* Timeline
* Related events
* Investigation findings
* Analyst conclusion
* Recommended action
* Evidence location

Investigation reports should be stored in:

`../Reports/`

Evidence screenshots and supporting artifacts should be stored in:

`../Evidence/`

# Alert Triage

The first step is to determine whether the alert requires immediate attention.

The analyst should review:

* Alert timestamp
* Alert severity
* Rule ID
* Event ID
* Hostname
* Username
* Source IP
* Destination information where available
* Process information
* Command line
* Parent process
* Related events
* Detection description

The purpose of triage is to quickly understand **what happened, where it happened, when it happened, and who was involved**.

---

# Alert Context

A security alert should never be analyzed in isolation.

For example:

```
Failed Logon
     ↓
One Event ID 4625
     ↓
Possible User Error
```

compared with:

```
4625
 ↓
4625
 ↓
4625
 ↓
4625
 ↓
4624
 ↓
Successful Authentication
 ↓
Higher Investigation Priority
```

The surrounding events can significantly change the interpretation of an alert.

---

# Key Alert Fields

## Timestamp

Determine:

* When the event occurred
* Whether multiple events occurred within a short period
* Whether the activity happened during expected hours

Accurate timestamps are essential for timeline construction.

---

## Hostname

Identify the affected endpoint.

Determine:

* Which Windows system generated the alert
* Whether the host is a workstation or server
* Whether the system is expected to generate this type of activity

---

## User

Identify the account associated with the event.

Determine:

* Username
* Account type
* Privileged or standard account
* Whether the account normally performs the observed activity

---

## Source IP

Where available, identify the source IP address.

Determine:

* Local or remote source
* Internal or external address
* Whether the source is expected
* Whether other events originate from the same source

---

## Process Information

For process-related alerts, review:

* Process name
* Parent process
* Command line
* User context
* Execution time

Process information can provide important evidence about how an action was initiated.

---

# Authentication Alert Analysis

Authentication alerts should be investigated using the surrounding authentication activity.

Important events include:

* `4624` — Successful logon
* `4625` — Failed logon
* `4634` — Logoff
* `4672` — Special privileges assigned
* `4740` — Account lockout

---

## Failed Logon Analysis

When an Event ID `4625` alert is generated, investigate:

1. Username
2. Source IP
3. Logon type
4. Timestamp
5. Number of failures
6. Related successful logons
7. Account status
8. Whether the activity was expected

Example:

```
4625
Failed Logon
    ↓
Identify Account
    ↓
Identify Source
    ↓
Check Frequency
    ↓
Search Related Events
    ↓
Determine Context
```

---

# Repeated Authentication Analysis

Repeated failed authentication events can indicate:

* Password guessing
* Brute-force attempts
* Password spraying
* Misconfigured applications
* Scheduled tasks
* Incorrect stored credentials

The analyst should correlate:

```
Source IP
    +
Username
    +
Time Window
    +
Failure Count
    +
Successful Authentication
    ↓
Authentication Assessment
```

Do not classify repeated failures as malicious without considering the environment and context.

---

# Privileged Logon Analysis

For Event ID `4672`, determine:

* Account involved
* Logon type
* Timestamp
* Source
* Whether the account is expected to have privileges
* Related authentication events
* Related process execution

Example:

```
4672 Privileged Logon
        ↓
   Identify User
        ↓
  Verify Authorization
        ↓
  Review Source/Host
        ↓
  Correlate Events
        ↓
    Analyst Decision
```

---

# Process Alert Analysis

For process-related alerts, investigate the complete process chain.

Review:

* Process name
* Parent process
* Grandparent process where available
* Command line
* File path
* User
* Timestamp
* Related network activity

Example:

```
Parent Process
      ↓
Child Process
      ↓
Command Line
      ↓
User Context
      ↓
Network Activity
      ↓
Process Assessment
```

The parent-child relationship can provide useful context that is not visible from the process name alone.

---

# PowerShell Alert Analysis

PowerShell alerts require careful analysis because PowerShell is commonly used for legitimate administration.

Review:

* PowerShell version
* User
* Parent process
* Command line
* Script Block Logging
* Module logging
* Execution time
* Related processes
* Related network activity

A PowerShell alert should not automatically be classified as malicious.

---

# Suspicious PowerShell Indicators

Potentially suspicious indicators may include:

* Encoded commands
* Obfuscated commands
* Unexpected PowerShell execution
* Unusual parent process
* Execution by an unexpected user
* Download or remote execution behavior
* Commands inconsistent with normal administration

The analyst should correlate multiple indicators before assigning high confidence.

---

# Account Activity Analysis

For account-related alerts, investigate:

* Account name
* Account creator
* Time of creation
* Account modification
* Group membership changes
* Privilege changes
* Whether the activity was authorized

Relevant events include:

* `4720`
* `4738`
* `4740`

Example:

```
Account Change
      ↓
Identify Account
      ↓
Identify Actor
      ↓
Check Privileges
      ↓
Check Authorization
      ↓
Correlate Activity
      ↓
Analyst Decision
```

---

# Alert Correlation

Multiple alerts can provide stronger evidence than a single alert.

Example:

```
Failed Logon
     ↓
Failed Logon
     ↓
Failed Logon
     ↓
Successful Logon
     ↓
Privileged Logon
     ↓
Suspicious Process
     ↓
High-Confidence Investigation
```

Correlation helps analysts understand the sequence of activity.

---

A timeline should be created when investigating potentially suspicious activity.

Example:

| Time     | Event | Interpretation            |
| -------- | ----- | ------------------------- |
| 10:01:12 | 4625  | Failed authentication     |
| 10:01:15 | 4625  | Failed authentication     |
| 10:01:19 | 4625  | Failed authentication     |

The timeline helps determine the order and relationship of events.

# Alert Enrichment

Alert enrichment means adding additional context to the alert.

Useful enrichment includes:

* Host information
* User information
* IP information
* Process information
* Related Event IDs
* Previous activity
* Asset importance
* MITRE ATT&CK mapping
* Known baseline behavior

The more useful context an analyst has, the faster an alert can be assessed.

---

# False Positive Analysis

An alert may be legitimate even when the detection condition was correctly triggered.

Examples:

* Administrator performing maintenance
* Scheduled task
* Software deployment
* Security software
* Automated service
* User entering an incorrect password

The analyst should document why an alert is considered benign.

Example:

```
Alert Generated
      ↓
Investigate Context
      ↓
Confirm Authorized Activity
      ↓
No Malicious Indicators
      ↓
False Positive / Benign
      ↓
Document
      ↓
Close
```

---

# Suspicious Alert Classification

An alert should be escalated when evidence suggests potentially malicious activity.

Indicators may include:

* Multiple related suspicious events
* Unauthorized account activity
* Suspicious process execution
* Unusual PowerShell activity
* Repeated authentication attempts
* Privileged activity inconsistent with the baseline
* Suspicious source
* Unexpected persistence-related activity

The analyst should record the evidence supporting the decision.

---

# Alert Severity Assessment

Alert severity should be reassessed during investigation.

Consider:

* Confidence
* Scope
* Asset importance
* User privileges
* Persistence indicators
* Lateral movement indicators
* Credential abuse
* Business impact

A medium-severity alert can become high priority after additional evidence is discovered.

Likewise, an initially high-severity alert may be downgraded after legitimate activity is confirmed.

---

# Analyst Decision

Every investigated alert should reach a documented decision.

Possible outcomes:

### Benign

Activity is expected and no security concern is identified.

### False Positive

The detection triggered correctly according to its logic, but the activity is not security-relevant.

### Suspicious

The activity requires additional investigation or monitoring.

### Confirmed Incident

Available evidence indicates a security incident and incident response should begin.

# Alert Investigation Example

## Scenario

A repeated failed authentication detection is generated.

### Initial Alert

```
Rule: Repeated Failed Logons
Event: 4625
Host: Windows-Monitoring-VM
```

### Analyst Investigation

1. Identify affected account.
2. Identify source IP.
3. Review failed authentication count.
4. Review authentication time window.
5. Search for successful authentication.
6. Check account lockout events.
7. Review privileged logon activity.
8. Review process activity after successful authentication.
9. Determine whether the activity was expected.

### Possible Result

```
Multiple 4625 Events
        ↓
Same Source + Account
        ↓
Successful 4624
        ↓
Additional Suspicious Activity
        ↓
Escalate for Investigation
```

The conclusion must be based on evidence collected during the investigation.

# Common Alert Analysis Mistakes

Avoid:

* Investigating an alert without context
* Assuming every alert is malicious
* Ignoring false positives
* Ignoring successful authentication after repeated failures
* Focusing only on one Event ID
* Ignoring timestamps
* Ignoring the affected user
* Ignoring the source IP
* Closing alerts without documentation
* Escalating alerts without supporting evidence

**Raw Alert → Context → Evidence → Decision**

Strong alert analysis demonstrates the ability to:

* Triage security alerts
* Correlate events
* Build timelines
* Identify suspicious behavior
* Investigate authentication activity
* Analyze processes
* Analyze PowerShell activity
* Reduce false positives
* Document findings
* Escalate incidents appropriately

These are directly applicable skills for entry-level SOC analyst roles.

---

# Conclusion

Alert analysis converts a generated security alert into an evidence-based security decision.

The core workflow is:

**Alert → Triage → Context → Correlation → Investigation → Decision → Documentation → Escalation/Closure**

The key principle is:

**An alert is a signal, not a conclusion.**

The analyst must investigate the available evidence before deciding whether the activity is benign, suspicious, or an incident.

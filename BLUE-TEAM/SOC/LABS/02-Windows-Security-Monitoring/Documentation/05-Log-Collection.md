# Log Collection

## Purpose

The purpose of this document is to explain how Windows security telemetry is collected from the monitoring endpoint and made available for security monitoring, detection, and investigation.

Effective log collection ensures that security events generated on the Windows endpoint are available to the SOC analyst for analysis.

---

## Log Collection Overview

Windows generates security events locally through different event sources.

The collection workflow is:

```
Windows Activity
      ↓
Windows Event Generation
      ↓
Windows Event Logs
      ↓
Wazuh Agent
      ↓
Wazuh Manager
      ↓
Detection Rules
      ↓
Security Alerts
      ↓
SOC Investigation
```

The exact collection path depends on the monitoring tools configured in the lab.

---

## Objectives

The log collection process should provide visibility into:

* Authentication activity
* Account activity
* Privileged activity
* Process execution
* PowerShell activity
* System activity
* Application activity
* Sysmon telemetry
* Other security-relevant endpoint events

## Primary Log Sources

The Windows endpoint may provide telemetry from the following sources:

| Log Source  | Security Monitoring Purpose                            |
| ----------- | ------------------------------------------------------ |
| Security    | Authentication, accounts, privileges, process activity |
| System      | System and service activity                            |
| Application | Application events and errors                          |
| PowerShell  | PowerShell execution and scripts                       |
| Sysmon      | Enhanced endpoint telemetry                            |
| Wazuh       | Centralized collection and analysis                    |

The required sources should be enabled according to the monitoring objectives defined in the lab.

---

## Windows Security Log

The Security log is one of the most important sources for Windows security monitoring.

It can contain events related to:

* Successful logons
* Failed logons
* Logoffs
* Account creation
* Account modification
* Account deletion
* Account lockouts
* Privileged logons
* Process creation
* Security policy changes

Important Event IDs include:

* `4624` — Successful logon
* `4625` — Failed logon
* `4672` — Special privileges assigned
* `4688` — Process creation
* `4720` — User account created
* `4738` — User account changed
* `4740` — User account locked out

---

## System Log Collection

The System log provides visibility into operating-system-level activity.

It can support investigations involving:

* Service changes
* Driver activity
* System startup
* System shutdown
* System errors
* Operating system events

System events may provide additional context when correlated with Security events.

---

## Application Log Collection

The Application log contains events generated by applications.

It can help identify:

* Application failures
* Unexpected application behavior
* Application startup problems
* Software-related events

Application events should normally be correlated with security telemetry rather than analyzed in isolation.

---

## PowerShell Log Collection

PowerShell telemetry can provide valuable visibility into script-based activity.

Depending on the configured logging level, useful events may include:

* PowerShell engine activity
* Module activity
* Script Block Logging
* PowerShell operational events

Important Event IDs include:

* `400`
* `403`
* `4103`
* `4104`

PowerShell logs should be correlated with process and authentication events during investigation.

---

## Sysmon Log Collection

When Sysmon is installed, its telemetry is available through:

`Microsoft-Windows-Sysmon/Operational`

Potential telemetry includes:

* Process creation
* Network connections
* File creation
* Registry activity
* DNS queries
* Process access
* Other endpoint activity

Sysmon provides additional context that can improve endpoint investigations.

---

## Wazuh Collection

When Wazuh is used, the Wazuh agent installed on the Windows endpoint can collect configured Windows event channels and forward them to the Wazuh manager.

The general architecture is:

```
Windows Event Sources
        ↓
   Wazuh Agent
        ↓
  Network Transport
        ↓
   Wazuh Manager
        ↓
   Event Analysis
        ↓
  Detection Rules
        ↓
      Alerts
```

The Wazuh configuration should collect only the logs required for the monitoring objectives.

## Windows Event Collection Verification

Before relying on centralized collection, verify the events locally.

### Step 1 — Generate Activity

Perform controlled activity such as:

* Normal user login
* Controlled failed login
* Normal process execution
* Benign PowerShell command

### Step 2 — Check Event Viewer

Open:

`Event Viewer`

Review the appropriate event channel.

### Step 3 — Identify the Event

Record:

* Event ID
* Timestamp
* Computer
* User
* Process
* Source
* Relevant event details

### Step 4 — Compare With Centralized Telemetry

If Wazuh is configured, verify that the same activity is visible through Wazuh.

---

## Wazuh Collection Verification

Use the following validation process:

1. Confirm the Windows endpoint is running.
2. Confirm the Wazuh agent service is running.
3. Confirm the agent is connected to the Wazuh manager.
4. Generate controlled Windows activity.
5. Check the relevant Windows event log.
6. Check whether Wazuh receives the event.
7. Review the resulting alert when a detection rule matches.
8. Compare the centralized event with the original Windows event.

This verifies the complete collection pipeline.

## Event Integrity

Collected logs should preserve important contextual information.

Important fields include:

* Timestamp
* Hostname
* Event ID
* User/account
* Source
* Process
* Command line
* IP address where available
* Event description
* Log source

Missing fields can reduce the analyst's ability to investigate an alert.

---

## Time Synchronization

Accurate timestamps are important for incident investigation.

Ensure that the Windows endpoint and monitoring infrastructure use appropriate system time settings.

Accurate time allows analysts to:

* Build reliable timelines
* Correlate multiple events
* Identify event sequences
* Compare endpoint and network activity
* Determine the order of actions

---

## Log Filtering

Not every event needs to become a security alert.

Log collection and alert generation are different processes.

```
Log Collection
      ↓
Large Event Set
      ↓
Detection Rules
      ↓
Relevant Alerts
```

The objective is to retain useful telemetry while avoiding unnecessary monitoring noise.

---

## Log Retention

The lab should retain sufficient logs to support investigation exercises.

Retention requirements depend on:

* Available storage
* Event volume
* Lab duration
* Investigation requirements
* Monitoring objectives

Important evidence should be preserved separately when required.

## Baseline Collection

Before running security scenarios, collect normal endpoint activity.

Examples:

* Normal logons
* Normal process execution
* Normal PowerShell activity
* Normal system activity
* Normal application events

This baseline helps distinguish normal behavior from anomalous activity.

Perform controlled tests to verify different telemetry sources.

### Authentication Test

Generate:

* Successful authentication

Verify the corresponding events.

### Process Test

Start a normal application.

Verify:

* Process creation

### PowerShell Test

Execute a benign PowerShell command.

Verify that the expected PowerShell telemetry is collected.

### Sysmon Test

If Sysmon is installed, generate normal process or network activity and verify that Sysmon records the activity.

## Troubleshooting

If events are visible locally but not centrally, investigate the collection pipeline.

Check:

* Windows Event Log service
* Correct event channel
* Wazuh agent status
* Wazuh agent configuration
* Wazuh manager status
* Network connectivity
* Collection configuration
* Event filtering
* Time synchronization

A useful troubleshooting approach is:

```
Event Generated?
      ↓
     Yes
      ↓
Visible Locally?
      ↓
     Yes
      ↓
Collected by Agent?
      ↓
     Yes
      ↓
Received by Manager?
      ↓
     Yes
      ↓
Detection Rule Applied?
      ↓
     Yes
      ↓
    Alert
```

This allows the analyst to identify exactly where telemetry is being lost.

## Professional SOC Relevance

Log collection is a core SOC capability.

An analyst cannot reliably detect or investigate threats when the required telemetry is missing.

Understanding log collection helps analysts:

* Identify telemetry gaps
* Validate monitoring infrastructure
* Troubleshoot missing events
* Correlate security events
* Build investigation timelines
* Improve detection quality
* Support incident response

## Conclusion

Reliable log collection connects endpoint activity with security monitoring and detection.

The objective is not simply to collect large volumes of events.

The objective is to ensure that the **right security telemetry is available, complete, timely, and usable for investigation**.

The next stage is to use this telemetry to create and validate security detection rules.

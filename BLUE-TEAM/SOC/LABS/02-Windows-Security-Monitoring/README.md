# Windows Security Monitoring Lab

## 1. Overview

This laboratory focuses on monitoring Windows endpoints and analyzing Windows security telemetry using a SOC-oriented approach.

The objective is to understand how Windows generates security events, how those events can be collected and monitored, and how a SOC analyst can use them to identify suspicious activity.

This lab builds upon the Wazuh SIEM environment and provides practical experience with Windows security monitoring.

---

## 2. Objectives

The main objectives of this lab are:

- Understand Windows security monitoring.
- Identify important Windows event sources.
- Understand Windows Event Logs.
- Monitor authentication activity.

- Monitor service activity.
- Collect Windows telemetry through Wazuh.

- Analyze Windows security alerts.

- Document findings and evidence.

## 9. Windows Event Logs

Windows provides several major event-log categories.

### Security Log

Contains security-related events such as:

- Authentication
- Account activity
- Security policy activity
- Privilege-related activity
- Object access where auditing is enabled

### System Log

Contains events generated by:

- Windows system components
- Drivers
- Services
- System state changes

### Application Log

Contains events generated by applications running on Windows.

### PowerShell Logs

Where configured, PowerShell logging can provide additional visibility into PowerShell activity.

### Sysmon Logs

When Sysmon is deployed, additional endpoint telemetry may include:

- Process creation
- Network connections
- File activity
- Process relationships
- Other security-relevant endpoint events

## 11. Authentication Monitoring

Authentication monitoring is an important SOC responsibility.

Monitor:

- Successful logons
- Failed logons
- Logon types
- Usernames
- Source systems
- Authentication frequency
- Authentication timing

Questions for the analyst:

- Who authenticated?
- From where?
- When?
- Was the authentication successful?
- Is the activity expected?
- Are there repeated failures?
- Is there a successful login following multiple failures?

---

## 12. Failed Login Monitoring

Failed login events can provide useful security signals.

Potential causes include:

- Incorrect password
- User error
- Expired credentials
- Misconfigured applications
- Automated services
- Password spraying
- Brute-force activity

A single failed login is generally insufficient to conclude that an attack occurred.

Look for:

- Frequency
- Source
- Target accounts
- Time pattern
- Related successful authentication
- Other endpoint activity

---

## 13. Successful Login Monitoring

Successful authentication events should also be monitored.

Investigate when:

- Login occurs at unusual times.
- Login originates from an unexpected system.
- Privileged accounts authenticate unexpectedly.
- Successful authentication follows repeated failures.
- Authentication is inconsistent with expected behavior.

Context is essential when evaluating successful logons.

---

## 14. Logon Types

Windows authentication events may include different logon types.

Common examples include:

| Logon Type | General Meaning |
|------------|-----------------|
| 2 | Interactive |
| 3 | Network |
| 4 | Batch |
| 5 | Service |
| 7 | Unlock |
| 8 | NetworkCleartext |
| 9 | NewCredentials |
| 10 | RemoteInteractive |
| 11 | CachedInteractive |

Understanding logon types helps analysts determine how authentication occurred.

## 15. Process Monitoring

Process execution is important endpoint telemetry.

A SOC analyst may investigate:

- Process name
- Process path
- Parent process
- User
- Command line
- Timestamp
- Process ID
- Network activity

Process monitoring becomes significantly more useful when combined with Sysmon or equivalent endpoint telemetry.

---

## 16. Account Monitoring

Monitor important account-related events.

Examples include:

- New account creation
- Account deletion
- Account enablement
- Account disablement
- Account modification
- Password-related activity
- Account lockouts
- Privileged account changes

Unexpected account changes should be investigated.

---

## 17. Privileged Activity Monitoring

Privileged accounts have greater security impact.

Monitor:

- Administrative logons
- Privilege assignments
- Administrative account changes
- Privileged process execution
- Changes to security configuration

An unusual privileged event should be correlated with other telemetry before classification.

---

## 18. Service Monitoring

Windows services can be important from both operational and security perspectives.

Monitor:

- Service creation
- Service startup
- Service stopping
- Service configuration changes
- Unexpected service activity

Investigate services that are:

- Unknown
- Newly created
- Running from unusual locations
- Associated with suspicious processes

---

## 19. PowerShell Monitoring

PowerShell is a legitimate administrative technology and can also be abused.

Monitoring should focus on:

- PowerShell execution
- User
- Command line
- Script activity
- Parent process
- Network activity
- Related events

Avoid treating every PowerShell event as malicious.

The investigation should focus on context and behavior.

## 22. Failed Login Investigation Exercise

### Objective

Generate controlled failed authentication attempts and observe the resulting telemetry.

### Procedure

1. Use the authorized Windows laboratory account.
2. Perform controlled unsuccessful authentication attempts.
3. Open Windows Event Viewer.
4. Locate the relevant Security events.
5. Record the event timestamp.
6. Identify the account.
7. Identify the source information where available.
8. Review the event in Wazuh.
9. Compare both data sources.

### Expected Learning

The analyst should understand:

- How failed authentication appears.
- Which event ID is generated.
- How Wazuh receives the event.
- What information can support an investigation.

---

## 23. Successful Login Investigation Exercise

### Objective

Observe a normal successful authentication event.

### Procedure

1. Authenticate using an authorized account.
2. Locate the corresponding Windows event.
3. Record the timestamp.
4. Identify the username.
5. Identify the logon type.
6. Review the Wazuh event.
7. Compare the event with expected behavior.

### Expected Learning

The analyst should understand the difference between normal authentication and suspicious authentication patterns.

## 32. False Positive Analysis

A Windows event does not automatically indicate malicious behavior.

Potential legitimate causes include:

- User mistakes
- Administrative activity
- Software updates
- Scheduled tasks
- System services
- Automated applications
- IT maintenance

The analyst should explain why an event was classified as benign or suspicious.

## 34. Investigation Questions

For every important Windows security alert, ask:

1. What happened?
2. When did it happen?
3. Which host was affected?
4. Which user was involved?
5. What process was involved?
6. How did the activity begin?
7. What happened immediately before the event?
8. What happened immediately after it?
9. Was the behavior expected?
10. Are there related events?
11. Is there evidence of compromise?
12. What action should the analyst take?

---

## 35. Recommended Response

### Benign Event

- Document the event.
- Close the alert if appropriate.
- Consider detection tuning.

### Suspicious Event

- Continue investigation.
- Collect additional telemetry.
- Search for related activity.
- Consider escalation.

### Confirmed Incident

- Escalate according to the incident-response process.
- Preserve evidence.
- Contain the affected endpoint where appropriate.
- Investigate scope.
- Document the incident.

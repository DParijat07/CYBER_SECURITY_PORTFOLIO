# Wazuh SIEM Lab — Alert Analysis

## 1. Purpose

This document covers the alert-analysis phase of the Wazuh SIEM laboratory.

The objective is to learn how a SOC analyst receives, validates, prioritizes, investigates, and documents security alerts generated by Wazuh.

The core workflow is:

Security Event
      ↓
Log Collection
      ↓
Detection Rule
      ↓
Wazuh Alert
      ↓
Alert Triage
      ↓
Context Analysis
      ↓
Severity Assessment
      ↓
False Positive / Suspicious / Confirmed
      ↓
Investigation
      ↓
Documentation

All testing must be performed only against authorized laboratory systems.

---

## 2. Alert Analysis Objectives

After completing this phase, the learner should be able to:

1. Understand the purpose of a SIEM alert.
2. Distinguish events from alerts.
3. Identify important Wazuh alert fields.
4. Interpret alert severity.
5. Identify the affected endpoint.
6. Identify the source of an alert.
7. Analyze authentication-related alerts.
8. Analyze endpoint-related alerts.
9. Analyze file-integrity alerts.
10. Analyze Sysmon-based alerts where available.
11. Perform basic alert triage.
12. Identify false positives.
13. Identify suspicious activity.
14. Escalate potentially malicious activity.
15. Document alert-analysis findings.

---

## 3. What Is a Wazuh Alert?

A Wazuh alert is generated when collected telemetry matches detection logic or another configured security condition.

Simplified workflow:

Endpoint Activity
       ↓
Log/Event
       ↓
Wazuh Agent
       ↓
Wazuh Manager
       ↓
Decoder
       ↓
Detection Rule
       ↓
Alert

The alert provides information that helps the SOC analyst determine whether further investigation is necessary.

---

## 4. Event vs Alert

### Event

An event is an observable activity generated by a system.

Examples:

- User Login
- Process Started
- File Modified
- Service Started
- Network Connection

### Alert

An alert is a security notification produced when telemetry satisfies a detection condition.

Therefore:

Event ≠ Alert

Not every event represents malicious activity, and not every event generates an alert.

## 5. Alert Triage

Alert triage is the initial process of determining the significance of an alert.

A basic triage workflow is:

Receive Alert
     ↓
Validate Alert
     ↓
Identify Asset
     ↓
Identify User
     ↓
Identify Activity
     ↓
Check Timestamp
     ↓
Review Context
     ↓
Assess Severity
     ↓
Determine Next Action

---

## 6. First Questions for an Analyst

When an alert appears, ask:

1. What happened?
2. When did it happen?
3. Which endpoint was affected?
4. Which user was involved?
5. What process or service was involved?
6. What was the source of the activity?
7. Was the activity expected?
8. Does the activity match normal behavior?
9. Are there related alerts?
10. Is additional investigation required?

---

## 7. Important Alert Fields

When examining an alert, review relevant fields such as:

- Timestamp
- Agent name
- Agent ID
- Host IP
- Rule ID
- Rule description
- Alert level
- Event source
- Username
- Process information
- Source IP
- Destination IP
- File path
- Event ID
- Command information
- MITRE ATT&CK information where available

Not every alert contains every field.

---

## 8. Alert Timestamp

The timestamp establishes when the activity occurred.

Check:

Alert Time
     ↓
Endpoint Event Time
     ↓
Related Events

Timestamp analysis is important for building an accurate incident timeline.

Always consider:

- Time zone
- Clock synchronization
- Event-processing delay
- Log-ingestion delay

---

## 9. Affected Asset

Determine which endpoint generated the alert.

Example:

Agent:
WIN-ENDPOINT

or:

Agent:
LINUX-ENDPOINT

Then determine:

- Operating system
- IP address
- Asset role
- Importance of the system
- Whether the system is expected to generate the activity

---

## 10. User Context

Determine whether a user account is associated with the event.

Example:

Username:
LAB-USER

Questions to ask:

- Is the account legitimate?
- Is the user expected to perform the activity?
- Is the account privileged?
- Has the account generated similar activity?
- Is the activity consistent with the user's role?

A valid username does not automatically make an event legitimate.

---

## 11. Rule Information

Review the Wazuh rule information.

Important fields include:

Rule ID
Rule Description
Rule Level
Rule Group

The rule description explains what condition triggered the alert.

Do not rely only on the rule name.

Always review the underlying event context.

---

## 12. Alert Severity

Wazuh alerts contain a severity or level.

A simplified interpretation is:

Low
 ↓
Medium
 ↓
High
 ↓
Critical

The exact level and meaning depend on the Wazuh rule and configuration.

Severity should be treated as a prioritization signal rather than absolute proof of malicious activity.

---

## 13. Severity Is Not Verdict

A high-severity alert does not automatically mean:

Confirmed Attack

Likewise, a low-severity alert does not automatically mean:

Safe

The analyst should correlate:

Severity
+
Context
+
Asset
+
User
+
Timeline
+
Related Events

before deciding the appropriate response.

## 14. Authentication Alert Analysis

Authentication alerts are common SOC use cases.

Examples include:

- Failed login
- Successful login
- Invalid username
- Multiple failed attempts
- Privileged account login

Basic investigation:

Authentication Alert
       ↓
Identify User
       ↓
Identify Source
       ↓
Check Time
       ↓
Count Attempts
       ↓
Check Successful Login
       ↓
Correlate Activity

---

## 15. Failed Authentication Analysis

A single failed authentication may be normal.

For example:

One failed login

may simply indicate that a user entered an incorrect password.

However:

Many failed logins
       ↓
Same Account
       ↓
Same Source
       ↓
Short Time Period

may require additional investigation.

---

## 16. Authentication Pattern Analysis

Look for patterns rather than isolated events.

Example:

18:01 Failed Login
18:02 Failed Login
18:02 Failed Login
18:03 Failed Login
18:03 Successful Login
18:04 Privileged Activity

This sequence may deserve closer investigation because multiple related events occur in a short time window.

The sequence alone does not prove compromise.

---

## 17. Process Activity Analysis

Process-related alerts should be analyzed using context.

Review:

- Process name
- Parent process
- Command line
- User
- Timestamp
- Executable path
- Network activity
- Related file activity

Useful investigation model:

Process
   ↓
Parent Process
   ↓
Command Line
   ↓
User
   ↓
Network / File Activity

This provides more context than looking at the process name alone.

---

## 18. PowerShell Alert Analysis

PowerShell activity should be evaluated in context.

Questions include:

- Who executed PowerShell?
- Was PowerShell expected?
- What was the parent process?
- What command or script was executed?
- What files were accessed?
- Were network connections created?
- Did additional alerts occur?

PowerShell itself is not malicious.

The analyst should determine whether the activity is authorized and consistent with expected behavior.

---

## 19. Sysmon Alert Analysis

If Sysmon is configured, related telemetry can provide additional context.

Potential areas of investigation include:

- Process creation
- Network connection
- File creation
- DNS activity
- Registry changes
- Process access

A useful approach is to correlate multiple events.

Example:

Process Created
      ↓
Network Connection
      ↓
File Created
      ↓
Additional Alert

The combination may provide stronger investigative context than any individual event.

---

## 20. File Integrity Alert Analysis

File-integrity alerts indicate that a monitored file or directory changed.

The analyst should determine:

- Which file changed?
- What type of change occurred?
- When did it occur?
- Which endpoint was affected?
- Was the change expected?
- Was there an authorized administrator activity?
- Are there related process or authentication events?

Workflow:

File Change
    ↓
Identify File
    ↓
Identify User / Process
    ↓
Check Change Time
    ↓
Check Related Events
    ↓
Determine Legitimacy

---

## 21. Linux Authentication Alert Analysis

For Linux authentication alerts, review:

- Username
- Source IP
- Authentication result
- Authentication method
- Timestamp
- Number of attempts
- Successful login following failures
- Privilege changes

Example investigation:

Failed SSH Attempts
        ↓
Same Source
        ↓
Same Account
        ↓
Successful Authentication
        ↓
Shell Activity

This sequence may warrant investigation in a controlled SOC scenario.

---

## 22. Alert Correlation

Correlation means analyzing multiple related events together.

Example:

Failed Authentication
        +
Successful Authentication
        +
New Process
        +
Network Connection
        +
File Modification

Individually, these events may have legitimate explanations.

Together, they may indicate suspicious behavior.

---

## 23. Alert Investigation Window

Do not investigate only the exact timestamp of an alert.

Examine a reasonable time window around the event.

Example:

Before Alert
     ↓
Alert
     ↓
After Alert

This can reveal:

- Preceding authentication attempts
- Process creation
- File changes
- Network connections
- Additional alerts
- Post-event activity

The appropriate window depends on the event.

---

## 24. False Positive Analysis

A false positive occurs when an alert is generated for activity that is not actually malicious.

Examples:

Authorized Administrator
       ↓
Legitimate Configuration Change
       ↓
Security Alert

or:

Security Tool
       ↓
Expected Scan
       ↓
Detection Rule Triggered

The analyst should document why the event was considered legitimate.

---

## 25. False Positive Investigation

Ask:

1. Is the activity expected?
2. Is the user authorized?
3. Is the asset performing a known task?
4. Is there a maintenance window?
5. Is the process legitimate?
6. Are there supporting logs?
7. Is the alert reproducible under normal conditions?

If the activity is legitimate, document the evidence.

---

## 26. Suspicious Alert Classification

An alert can be classified as suspicious when:

- Activity is unusual.
- The user is unexpected.
- The process is unusual.
- The source is unfamiliar.
- Multiple related events occur.
- The behavior deviates from the expected baseline.

Suspicious does not necessarily mean confirmed malicious.

---

## 27. Confirmed Malicious Activity

A laboratory alert may be classified as confirmed malicious when sufficient evidence demonstrates that the observed activity violates the defined security scenario.

A useful model is:

Initial Alert
     ↓
Evidence Collection
     ↓
Event Correlation
     ↓
Behavior Analysis
     ↓
Supporting Evidence
     ↓
Confirmed Finding

Avoid declaring an incident based on a single unexplained alert when additional evidence can be collected.

---

## 28. Alert Classification

Use a simple classification model:

| Classification | Meaning |
|---|---|
| Informational | Useful security telemetry |
| Benign | Expected legitimate activity |
| False Positive | Detection triggered incorrectly or unnecessarily |
| Suspicious | Activity requires additional investigation |
| Confirmed Malicious | Evidence supports malicious activity |

The exact categories can be adapted to the laboratory's SOC workflow.

---

## 29. Alert Priority

Priority should consider more than severity.

Consider:

Alert Severity
+
Asset Criticality
+
User Privilege
+
Confidence
+
Business Impact
+
Correlated Events

Example:

Medium Alert
+
Privileged Account
+
Critical Server
+
Multiple Related Events

may deserve higher priority than an isolated high-level alert on a low-value test endpoint.

 ↓

 ↓

 ↓
Investigate
 ↓

 ↓

## 40. Common Alert-Analysis Mistakes

Avoid:

### Looking Only at Severity

Severity does not provide the complete context.

### Looking at One Event

Related events may change the interpretation.

### Ignoring the User

User context can determine whether activity is expected.

### Ignoring the Asset

The same event can have different significance depending on the system.

### Ignoring Time

Timeline analysis is essential.

### Closing Alerts Without Evidence

Always document the reason for closure.

### Treating Every Anomaly as Malicious

Unusual activity requires investigation, not automatic classification.

When did it happen?

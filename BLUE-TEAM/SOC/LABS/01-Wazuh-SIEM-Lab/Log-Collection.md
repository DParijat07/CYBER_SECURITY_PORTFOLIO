# Wazuh SIEM Lab — Log Collection

## 1. Purpose

This document covers the log and security-telemetry collection phase of the Wazuh SIEM laboratory.

The objective is to verify that security data generated by monitored endpoints is successfully collected by Wazuh, processed by the Wazuh Manager, indexed, and made available for SOC monitoring and investigation.

The complete workflow is:

```text
Endpoint
   ↓
Security Event
   ↓
Local Log Source
   ↓
Wazuh Agent
   ↓
Wazuh Manager
   ↓
Decoder / Analysis
   ↓
Indexer
   ↓
Wazuh Dashboard
   ↓
SOC Analyst
```

All activities must be performed only against authorized laboratory systems.

---

## 2. Log Collection Objectives

After completing this phase, the learner should be able to:

1. Explain the purpose of security-log collection.
2. Identify important endpoint telemetry sources.
3. Understand how Wazuh agents collect telemetry.
4. Verify agent-to-manager communication.
5. Configure selected Windows event sources.
6. Configure selected Linux log sources.
7. Verify Sysmon telemetry where applicable.
8. Generate controlled test events.
9. Confirm that events reach the Wazuh Manager.
10. Locate collected events in the Wazuh Dashboard.
11. Understand the difference between raw events and alerts.
12. Troubleshoot missing or incomplete telemetry.
13. Document successful log collection.

---

## 3. Why Log Collection Matters

A SOC analyst can only investigate activity for which useful telemetry exists.

The relationship can be represented as:

```text
No Telemetry
     ↓
No Visibility
     ↓
Limited Detection
     ↓
Limited Investigation
```

Effective telemetry collection therefore forms the foundation of:

- Security monitoring
- Detection
- Alert triage
- Threat hunting
- Incident response
- Digital forensics

## 7. Windows Security Events

The Windows Security log can provide valuable authentication and account-management telemetry.

Potential events include:

- Failed logon
- Successful logon
- Account creation
- Account modification
- Account deletion
- Privilege-related activity
- Logon/logoff activity

The learner should generate only controlled test activity.

---

## 8. Windows System Events

The System log provides information about operating-system activity.

Potential information includes:

- Service activity
- Driver activity
- System startup
- System shutdown
- System errors
- Hardware-related events

These events can provide additional context during investigations.

---

## 9. Windows Application Events

Application logs may provide information about:

- Application errors
- Service failures
- Application startup
- Application configuration
- Application-specific security events

Application telemetry can be useful when investigating suspicious activity involving a particular service or application.

---

## 10. PowerShell Telemetry

PowerShell is commonly used for legitimate administration and automation, but it can also be abused by attackers.

Relevant telemetry can provide context about:

- PowerShell execution
- Commands
- Scripts
- Errors
- Administrative activity

Where appropriate, collect PowerShell-related event channels in the laboratory.

---

## 11. Sysmon Telemetry

When Sysmon is installed and configured on the Windows endpoint, it can provide enhanced endpoint visibility.

Common telemetry categories include:

- Process creation
- Network connections
- File creation
- Registry activity
- DNS activity
- Process access
- Driver activity

The actual telemetry depends on the installed Sysmon version and configuration.

---

## 12. Linux Log Sources

Linux telemetry varies by distribution and logging architecture.

Common sources include:

```text
/var/log/auth.log
/var/log/secure
/var/log/syslog
/var/log/messages
```

Modern Linux systems may also rely heavily on:

```text
systemd-journald
```

Always determine which logging mechanism is used by the laboratory system.

---

## 13. Linux Authentication Logs

Authentication logs are particularly important for SOC monitoring.

Relevant activity can include:

- Failed login
- Successful login
- Invalid user
- SSH activity
- Privilege escalation
- Authentication errors

These events can help identify suspicious authentication patterns.

---

## 14. Linux SSH Telemetry

SSH is a common source of authentication telemetry.

A controlled laboratory exercise can generate several unsuccessful authentication attempts against the learner's own test system.

The resulting logs can be used to investigate:

```text
Source
   ↓
Username
   ↓
Authentication Attempt
   ↓
Result
   ↓
Timestamp
```

Do not perform authentication attempts against systems that you do not own or have permission to test.

## 15. Linux System Logs

System logs can provide information about:

- Services
- System events
- Errors
- Configuration changes
- Kernel-related activity
- Scheduled tasks

These logs can help establish context during an investigation.

## 16. Wazuh Agent Collection

The Wazuh agent is responsible for collecting configured telemetry from the endpoint.

Conceptually:

```text
Local Event
    ↓
Configured Log Source
    ↓
Wazuh Agent
    ↓
Wazuh Manager
```

If the event exists locally but does not reach Wazuh, the investigation should begin at the collection stage.

---

## 17. Verify Agent Status

Before testing log collection, verify that the agent is operational.

On Linux:

```bash
sudo systemctl status wazuh-agent
```

On Windows, verify the Wazuh Agent service through the Windows Services interface.

The agent should be running and connected to the Wazuh Manager.

---

## 18. Verify Agent Connection

From the Wazuh Dashboard, verify:

- Agent name
- Agent ID
- Operating system
- IP address
- Connection status
- Last communication

Expected state:

```text
Agent
  ↓
Connected
  ↓
Active
```

If the agent is disconnected, troubleshoot connectivity before continuing.

---

## 19. Generate a Controlled Windows Event

Use an authorized Windows test endpoint to generate a harmless event.

Examples include:

- Creating a test account where appropriate
- Logging in with a test account
- Generating a controlled failed authentication
- Starting or stopping a test service
- Creating a test file
- Running a benign test process

The objective is to generate observable telemetry, not to compromise the endpoint.

---

## 20. Generate a Controlled Linux Event

Use the Linux laboratory endpoint to generate harmless telemetry.

Examples include:

```bash
touch ~/soc-test-file.txt
```

or performing an authorized login/logout operation.

For authentication testing, use only test accounts and the laboratory system.

---

## 21. Verify the Local Event

Before troubleshooting Wazuh, verify that the endpoint actually generated the event.

For Linux, inspect the relevant log source.

Examples:

```bash
sudo tail -f /var/log/auth.log
```

or:

```bash
sudo journalctl -f
```

The exact command depends on the Linux distribution and logging system.

For Windows, use:

```text
Event Viewer
    ↓
Windows Logs
    ↓
Security / System / Application
```

## 22. Verify Wazuh Collection

After confirming that the event exists locally:

```text
Local Event
    ↓
Wazuh Agent
    ↓
Wazuh Manager
```

Search for the corresponding event in the Wazuh Dashboard.

Compare:

- Timestamp
- Hostname
- Username
- Event type
- Event details

This helps determine whether the correct event was collected.

---

## 23. Raw Event vs Alert

It is important to distinguish between an event and an alert.

### Event

A piece of telemetry generated by a system.

### Alert

A security notification generated when collected data matches detection logic or another alert condition.

The workflow is:

```text
Raw Event
    ↓
Collection
    ↓
Decoding
    ↓
Rule Evaluation
    ↓
Alert
```

Not every collected event necessarily becomes a security alert.

---

## 24. Event Timestamp Verification

Timestamps are critical for SOC investigations.

Compare:

```text
Endpoint Timestamp
        ↓
Wazuh Timestamp
        ↓
Dashboard Timestamp
```

Differences may indicate:

- Time-zone configuration
- Clock drift
- Time synchronization issues
- Logging delays

Accurate time is essential for reliable event correlation.

## 27. Missing Event Troubleshooting

If an expected event is not visible in Wazuh, investigate systematically.

### Step 1 — Confirm the Event Exists

Check the endpoint's local logs.

### Step 2 — Check the Agent

Verify that the Wazuh agent is running.

### Step 3 — Check Connectivity

Confirm that the endpoint can communicate with the Wazuh Manager.

### Step 4 — Check Configuration

Verify that the required log source is configured for collection.

### Step 5 — Check Manager

Confirm that the Wazuh Manager is operational.

### Step 6 — Check Event Processing

Determine whether the event is being received but not displayed as an alert.

### Step 7 — Check Dashboard

Verify search filters, time range, agent selection, and other query parameters.

---

## 28. Common Collection Problems

### Agent Offline

Possible causes:

- Service stopped
- Network problem
- Incorrect manager address
- Firewall restrictions
- Registration problem

### Logs Exist Locally but Not in Wazuh

Possible causes:

- Incorrect collection configuration
- Agent problem
- Unsupported or incorrect log source
- Configuration not reloaded
- Connectivity issue

### Event Exists but No Alert Appears

Possible causes:

- No matching detection rule
- Event parsing issue
- Alert threshold not reached
- Event classified as ordinary telemetry

## 33. Telemetry Quality

Good SOC telemetry should be:

### Relevant

It should support a monitoring or investigation objective.

### Accurate

It should reflect actual system activity.

### Timely

It should arrive with acceptable delay.

### Searchable

It should be accessible for investigation.

### Contextual

It should contain useful information such as host, user, process, timestamp, and event type.

---

## 34. Telemetry-to-Detection Relationship

Log collection alone does not guarantee detection.

The complete process is:

```text
Telemetry
    ↓
Collection
    ↓
Parsing / Decoding
    ↓
Detection Logic
    ↓
Alert
    ↓
Investigation
```

A mature SOC therefore requires both effective telemetry collection and effective detection engineering.

---

## 35. Security Considerations

Do not collect or publish unnecessary sensitive information.

Avoid publishing:

- Passwords
- API keys
- Tokens
- Private keys
- Personal information
- Sensitive production logs
- Confidential network information

Use laboratory accounts and test data whenever possible.
